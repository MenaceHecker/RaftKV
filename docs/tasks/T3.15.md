## Goal
Three small defects in `DiskStorage` (`internal/storage/disk.go`), none a Raft-protocol rule:
1. `DiskConfig.SnapshotsKept` is validated (`:50-56`) and then ignored: `CreateSnapshot` purges with `DefaultSnapshotsKept` (`:275`) and
   `ApplySnapshot` the same (`:330`). The field is not even stored on `DiskStorage`, and no caller outside this file sets it.
2. `Snapshot()` (`:278-301`) reads the newest snapshot's metadata under the read lock, **releases the lock**, then calls `LoadAt`.
   A concurrent `CreateSnapshot` can publish newer snapshots and purge the selected file in between, so `LoadAt` fails with
   `ErrNotExist`. With the default of 3 it needs three compactions inside the window; with `SnapshotsKept` honored at 1 a single one suffices.
3. `CreateSnapshot` sets `s.entries = compacted` (`:269`) **before** `TruncateBefore` (`:271`) and `Purge` (`:275`), and `ApplySnapshot` sets
   `s.entries` (`:325`) before `:327` and `:330`. A cleanup failure returns an error although the snapshot is already published
   and memory already compacted. T3.9 narrowed the claim "memory is never updated on failure"; this card pins and fixes the rest.

## Behavior specification (decided unless marked)
- **Retention.** Store `snapshotsKept` on `DiskStorage` from the validated config; use it at both purge sites. `Purge(keep)` already rejects
  `keep < 1` (`snapshot.go:330`). Open with the newest snapshot readable still falls back to older ones (`snapshot.go:164-186`), so
  `SnapshotsKept = 1` removes that fallback: document it in `DiskConfig`. Plumbing a node flag or `node.Config` field is not in scope (OPEN Q 1).
- **Race.** Recommended: no lock held across file IO. `Snapshot()` selects the metadata, calls `LoadAt`, and on `ErrNotExist` re-selects
  the (now newer) metadata and retries, bounded to 3 attempts, then returns the last error. Any committed snapshot is valid to serve: the
  returned `raft.Snapshot` carries its own Index and Term. **Retries mitigate, they do not guarantee**: an adversarial schedule can
  purge each selected snapshot before its read on all three attempts, so a transient `ErrNotExist` remains possible and callers must
  tolerate it (the raft layer retries on its next tick). Retry exhaustion is tested (test 4b). If a hard guarantee is ever required it needs
  a mechanism that pins the selected file (or a lock across `LoadAt`, rejected here). Rejected alternative: holding `s.mu.RLock` across
  `LoadAt` blocks writers for the duration of an up-to-64 MiB read.
- **Error-path relationship (what the table must show, then fix only the violations).** Define *publication* as the snapshot file saved
  (`Save`, fsynced and renamed) **and** the WAL meta record written. Before publication fails: memory unchanged; disk may be ahead
  (snapshot file present without the meta record: the next open loads the newer snapshot, `disk.go:69-91`, so memory and disk differ after
  restart; this is acceptable but must be documented and tested). After publication, cleanup failure (`TruncateBefore` Remove or SyncDir,
  `Purge` Remove or SyncDir): memory is already compacted and consistent with disk; the call returns an error wrapping a new
  `ErrSnapshotCleanup` so callers can tell "published, cleanup failed" from "not published". The ordering at `:269` / `:325` stays
  (memory follows the publication) and is documented, unless a table row shows an inconsistency.
- **Node reaction (OPEN Q 2).** T3.9 makes every `CreateSnapshot` error node-fatal. This card keeps that for WAL-side cleanup failures
  (they poison, T3.9) and proposes that a purge-only failure (`snapshot.go:344`, `:348`) be logged and survived.
