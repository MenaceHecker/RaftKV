## Goal
Add a standalone `chaosrun -sim` command that runs every chaos scenario plus one new seed-generated scenario (nemesis schedule and
workload from RUNBOOK 8.4/8.5) across a seed range, prints a per-seed verdict, and exits non-zero on any failure, so `-seeds 1-200`
can run in CI and `make chaos-smoke`. Any failure is reproducible from its printed seed (RUNBOOK 8.1). No Raft core change.

## What exists (chaos/, package `chaos`)
- Sim: `Cluster` of real `raft.Node`s on a virtual tick clock (`cluster.go:107,358`), seeded `Network` with loss, delay, duplicate,
  partition (`network.go:11,66,90`), crash/restart (`cluster.go:450,467`), membership and snapshot ops (`cluster.go:213-344`).
  Election safety is checked every tick (`cluster.go:391`); replicas compared by `Converged` (`cluster.go:786`).
- Seed use: one seed feeds the network RNG (`cluster.go:130`, `network.go:67`) and each node's Rand (`cluster.go:194`). The fault
  schedule itself is hard-coded per scenario; a seed varies message fate and election timeouts only.
- Checker: `Check` (`checker.go:72`) per-key linearizability with unknown ops. Ops are only write and read (`cluster.go:16-21`).
- Runner: `Scenario` (`scenario.go:13`), `RunScenario` (`:114`), `RunScenarioOnDisk` (`:118`), `runOnce` (`:131`, uses `SyncNever`
  at `:139`), `Report.String` (prints `seed N VERDICT ...`), minimal `Workload` (`:255`). `RunResult` keeps counts, not the history.
- 23 scenarios, **all in `chaos/scenarios_test.go`** (`allScenarios` at `:1055`), plus `TestChaosReport` (`:1139`) and
  `TestChaosOnDisk` (`:1202`). Because they live in a `_test.go` file, `cmd/chaosrun` cannot import them.
- `make chaos-smoke` today runs `go test ./chaos -run TestChaosReport` (Makefile; its comment says no `cmd/chaosrun` exists). That
  test rewrites `docs/chaos-report.md` with 5 seeds (`scenarios_test.go:14`).
- Not present: `cmd/chaosrun`, a JSONL history recorder (T5.2 has no card; STATUS lists it absent, `docs/STATUS.md:105`), any event
  trace, cas/delete ops, `faultinject` build tag, `internal/sim|verify` (RUNBOOK uses those names; real package is `chaos`).
- T4.7 admin API (`internal/transport/admin.go:56-70,174-217`): Status, Crash (calls `exit(137)`, no restart), Pause, SetPartition,
  SetNetem, Events. Usable later for a live mode; not used here.

RUNBOOK 7.1 Election Safety and State Machine Safety are the oracles (`cluster.go:391,786`) plus linearizability (8.3). Nothing in

## Decisions
1. **Move, do not copy.** Scenario constructors, `requireX` helpers, `settleMembership`, `requireSnapshotInstalled`, `sanitize`, and
   `allScenarios` (renamed `AllScenarios`, exported) move verbatim to `chaos/scenarios.go`. `Test*` funcs stay in the test file and
   still call the same unexported names. This deletes lines from a test file, so `guard-tests.sh` will flag it; the PR says so.
2. **Flags:** `-sim` (required), `-seeds SPEC` (`1-200`, `7`, `1,3,5-9`; default `1-20`), `-seed N` (one seed; mutually exclusive with
   `-seeds`), `-scenario SUBSTR` (case-insensitive substring; 0 matches is a usage error), `-list`, `-json` (one JSON object per
   run on stdout: scenario, seed, verdict, error, ticks, ok/failed/unknown; text goes to stderr), `-disk DIR` (use
   `RunScenarioOnDisk`, else in memory). Seeds must be >= 1; a range wider than 100000 is rejected.
3. **Exit codes:** 0 every run passed; 1 at least one run failed, errored, diverged or was non-linearizable (uses `RunResult.Passed`,
   `scenario.go:47`); 2 usage error (bad flag, no `-sim`, bad seed spec, unknown scenario). Never 0 when zero runs executed.
4. **Failure output:** one line per failing run `FAIL <scenario> seed <N>` and `reproduce: chaosrun -sim -seed N -scenario "<name>"`,
   followed by the existing `Report.String` detail. Passing runs print one summary line per scenario.
5. **Seed to schedule:** unchanged for the 23 scenarios. The new 24th, `generated nemesis and workload`, derives its schedule from
   `Schedule(seed int64) []Step` (pure, own `rand.New(rand.NewSource(seed ^ constant))`, never the cluster's RNG): 5 nodes, 3-5 clients,
   5-20 keys, unique values, 50/50 read/write (see OPEN QUESTIONS 2), then a sequence of steps drawn from {partition leader,
   split, isolate, crash, restart, set loss/delay/duplicate, compact} that always ends with Heal + restart of every node and a
   liveness check: a leader exists and a write succeeds within a tick bound (RUNBOOK 8.4). Needs `Cluster.Seed()` accessor.
6. **Determinism and trace.** The "event trace" is the full `[]Op` history (`History()`, `cluster.go:350`: kind, client, key, value,
   invoked, returned, status), `Stats`, and final `Ticks`. `RunResult` gains `History []Op` and `Digest string` (sha256 of a canonical
   text encoding). There is no per-message event log; adding one is out of scope.
7. **History file:** no JSONL. The recorder (T5.2) does not exist, so `chaosrun` writes nothing in 8.2 format. Failing text output
   only. When T5.2 lands, a `-history-dir` flag is a follow-up.
8. **Live mode:** out of scope. `-sim` stays mandatory so a later `-live -admin ...` flag does not change existing invocations. Admin
   `Crash` exits the process with no restart (`admin.go:174-181`), so live restarts need an external supervisor; noted for a later card.
9. **Interface for T5.7:** exported `chaos.AllScenarios()`, `chaos.ParseSeeds`, `chaos.RunSeeds(scenarios []Scenario, seeds []int64)
   []Report`, `RunResult.Digest`, and the CLI contract: `go run -tags faultinject ./cmd/chaosrun -sim -seeds A-B [-scenario S]`
   exits 1 when a seed catches the bug and 0 when it does not; `-json` is the machine-readable result. T5.7 owns the `faultinject` tag.

## Implementation notes
- Sequential execution, fixed scenario then seed order, so output is stable. No goroutines in `chaosrun`.
- `run` takes the scenario slice as a parameter so tests can inject failing scenarios without touching real ones.
- Generator must not read the cluster's or network's RNG (would perturb the other scenarios' streams); use its own `rand.Rand`.
- No `time.Now`/`time.Sleep` in `chaos` or `cmd/chaosrun` logic; progress is by ticks. Wall time is only printed by `main` if at all.
- Cite RUNBOOK 8.4/8.5 in `generated.go` comments. Commits are small (about 300 lines or less); (a) is large only because it is a move.

## Acceptance criteria
- `go run ./cmd/chaosrun -sim -seeds 1-200` exits 0 (RUNBOOK T5.6), run by the runner in a clean checkout.
- Same seed gives an identical history digest (test); a failure prints a working `reproduce:` line (RUNBOOK 8.1).
- Exit codes 0/1/2 as specified; `make chaos-smoke` runs `chaosrun` and exits 0.
- `make fmt vet lint test` green; `go test ./chaos -list .` unchanged except additions; no assertion removed or loosened;
  `guard-tests.sh origin/main` output attached, with the move explained.
