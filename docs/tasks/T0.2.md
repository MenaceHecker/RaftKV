# T0.2: keep the README test counts exact without hand-editing them

Planner: Claude, read-only. Based on `origin/main` f7c6246 (T3.18 merged). Claims come from reading; **no test was run**.
Branches: `test/t0-2-readme-counts-red`, then `chore/t0-2-readme-counts`. Tooling only; no change to `internal/raft`, storage or transport.

## Goal
`internal/determinism/readme_test.go` requires the README's test count to be exactly right. That is a good rule, but the number lives on two
README lines that every PR adding tests edits, so concurrent PRs conflict and a merge of main leaves a stale count. In the last week this
cost four hand-fixes (PRs #29 twice, #30, #31) and two red CI checks per stale count (the `build and test` and `mutation suite` jobs both run the test).
Make the number **generated** and the fix **one command**, with the test untouched and exactly as strict as today.

## Invariants touched
None in the Raft code. RUNBOOK §2 "never weaken a test": the existing test is **not edited**; no tolerance is added, nothing skipped.

## Facts from the code (f7c6246)
- `TestReadmeTestCountIsCurrent` (`readme_test.go:15`) counts `(?m)^func Test\w` and `^func Fuzz\w` over every `*_test.go`, and requires the README to
  say `N tests and <word> fuzz targets`, `across N tests`, and the fuzz word (`five`..`ten` only). `TestReadmeLineCountsAreRoughlyRight`
  allows 10% drift on the line counts; it rarely fails. `TestChaosReportMatchesTheScenarioCount` ties the README scenario word to
  `docs/chaos-report.md`.
- The file walk (`walkGo` in `readme_test.go`) skips only `.git`. A nested `.claude/worktrees/<agent>/` or any second checkout inside the repo
  is counted too: with one nested worktree the test saw 1381 tests (about double). Hit once in this project.
- The two README lines are `README.md:11` and `:179`. Both CI jobs `build and test` and `mutation suite` (`ci.yml:99`) run `internal/determinism`.
- Precedent for "generate in CI and diff": the mutation job regenerates `docs/CHAOS_RESULTS.md` with `WRITE_CHAOS_RESULTS=1` and diffs it.
- The Makefile has `.PHONY: fmt vet lint test test-flaky cover proto chaos-smoke`; the pre-commit hook runs gofmt, vet, `go test -race -short ./...`.

## Design (recommended): stay exact, make the fix mechanical
1. `internal/readmecounts` (non-test package): `Count(root string) (tests, fuzz, implLines, testLines int, err error)` using the **same** regexes and walk as the
   test, and `Rewrite(readme string, c Counts) (string, error)` that replaces only the four number sites (the two test counts, the fuzz word, the two line
   counts only when more than 5% out, rounded to the nearest 100). It **refuses** (error naming the path) if it meets a `.claude/` directory or a nested
   `.git` file, instead of silently double counting.
2. `cmd/readmecounts`: `-write` (default) rewrites `README.md`; `-check` exits 1 and prints the diff and the fix command when stale. Exit 2 on usage or refusal.
3. `make readme-counts` (write) and `make readme-check`. A `make sync-main` target runs `git fetch`, `git merge --no-edit origin/main`, then
   `make readme-counts`, and stops showing `git status` (it never commits or pushes). This is what was done by hand four times.
4. `.githooks/pre-commit`: run `go run ./cmd/readmecounts -check` first (about 1s), so a stale count fails with the exact command instead of after a
   full test run. The hook keeps running the unchanged test afterwards.
5. `ci.yml` `build and test`: add the same `-check` step before `go test`, so a stale count is one named, fast failure with the command to run.
6. `CLAUDE.md` Commands: add "after adding tests or merging main, run `make readme-counts`" (human reviews that diff). Executor prompts say the same.

## Acceptance criteria
`make readme-counts` on a stale README makes `go test ./internal/determinism` pass; `make sync-main` on a branch behind main with a conflicting count
needs no hand edit; a stale count fails the new CI step in seconds with the fix command; `readme_test.go` has **zero changed lines**
(`git diff origin/main -- internal/determinism/readme_test.go` is empty); `make fmt vet lint test`; `scripts/guard-tests.sh origin/main` exit 0.

## Out of scope
Loosening or removing any assertion; a tolerance or "at least N" claim; skipping the test in CI; a bot that commits to main; changing the README wording
the test matches; fixing the test's walk (see OPEN QUESTIONS 2).

## OPEN QUESTIONS for the human
1. **Conflicts still occur** (two PRs editing one line); this design makes every resolution one command, it does not remove them. To remove them you must
   stop committing the number per PR. Alternative B: README numbers are regenerated by a post-merge job that opens a `chore/readme-counts` PR for a human to
   merge, and PR CI runs the test against a regenerated copy. That makes the test self-satisfying in PR CI, so the committed README can lag main; it is a
   weaker guarantee even though no test code changes. Not recommended; say if you want it.
2. **The test's walk** includes `.claude/worktrees` and any nested checkout. The tool refuses such trees; fixing the walk itself changes the test (guard
   will flag it), so it needs your approval. Proposed: skip directories named `.claude` and `node_modules`, with a test proving a nested copy is not counted.
3. **Auto-fix bot** that pushes the regenerated README to same-repo PR branches: needs a token that triggers CI (commits by `GITHUB_TOKEN` do not), and the
   RUNBOOK says the human merges. Default off; propose only if the one-command fix is still too much friction.
4. **Line counts:** the tool rewrites them only when more than 5% out, rounded to 100, to avoid churn. Is that acceptable, or leave them manual?
