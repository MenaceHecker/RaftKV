# T3.7: repair a bad record at the tail of the last WAL segment

Planner: Claude, read-only. Based on `internal/storage` at 6018e7b. Branch: `fix/t3-7-torn-tail`. Depends on T3.6 merged (uses
`FS`). Merge order T3.6, T3.7, T3.8. Closes STATUS §5 #2 (the "bad CRC at the tail also refuses" half).

## Goal
`WAL.replay` repairs only `ErrTornRecord` at the tail of the last segment (`wal.go:200`). A bad CRC, an oversize length or a zeroed
tail there makes the node refuse to start, while RUNBOOK §7.3 calls these a torn write. Truncate when nothing valid follows the
bad record in the last segment; otherwise keep returning `ErrCorruptWAL`. Count and log every repair.

## Invariants touched (RUNBOOK §7 refs)
§7.3 #2 (this card); §7.2 item 1 and §7.3 #3 (the repair must not touch acked data that is still readable, and the repair itself
must be durable); §7.3 #4 (garbage tail after a crash; the faultfs cases are in T3.8).

## Behavior specification (decided)
- Last segment only. Any error in an older segment stays `ErrCorruptWAL` (`wal.go:196-199`; `wal_test.go:320`).
- Bad record: the first offset `good` where `readRecord` fails with `ErrTornRecord`, `ErrCorruptRecord` or `ErrRecordTooLarge`.
- Truncate **only if** no offset `p > good` in the remainder of that segment holds a valid record: `readRecord` succeeds, the type is
  known, and the payload decodes (`decodeEntry`, `decodeHardState`, `decodeSnapshotMeta`). Scan cost is O(segment bytes).
  If one is found, damage is mid-log: `ErrCorruptWAL` naming segment and offset.
- A record with a valid CRC whose type is unknown or whose payload fails to decode is **corruption, not a tear**: refuse
  (`replaySegment` already returns these, `wal.go:229-251`); never reaches the repair path.
- Repair steps: `FS.Truncate` to `good`; open the file, `Sync` it, close; `SyncDir`; set `Replay.Repaired`. Today only `SyncDir` runs
  (`wal.go:206-211`), so the new size is not durable; this adds the file fsync.
- On repair: `slog.Warn` with segment, offset, bytes dropped and the original error; and the counters below. **No flag** disables it.
- Documented residual risk (code comment): a fsynced record later rotted by the media, with nothing valid after it, is
  indistinguishable from a tear and is dropped. The valid-data-follows rule keeps this to the final record(s).

## Metrics
- `internal/metrics`: two counters, namespace `raftkv`: `wal_repairs_total` (one per repair) and `wal_repair_dropped_bytes_total` (bytes truncated).
  Documented in `docs/observability.md` (`internal/metrics/deployed_test.go:20` checks that every `raftkv_*` reference in docs exists).
- Bytes dropped is `len(segment) - good`. There is no per-record counter: the garbage after the first bad frame cannot be framed or counted.
- `storage` must not import Prometheus. Add `Options.OnRepair`, `DiskConfig.OnRepair func(RepairInfo)` with
  `RepairInfo{Segment string; Offset, Bytes int64; Cause error}`. `internal/node` passes a closure that calls a new
  `Recorder.WALRepaired(bytes int64)` (adds 1 to repairs, `bytes` to dropped bytes), set up before `OpenDiskStorage` (`node.go:190`; `applyDefaults` runs first).
  Update `nopRecorder` (`internal/node/metrics.go:60`) and any fake `Recorder` in tests.

## Implementation notes
- Keep `ErrTornRecord` handling; extend the repairable error set only through the "nothing valid follows" check.
- A short final record with a plausible header is `ErrTornRecord` or `ErrRecordTooLarge`; both go through the same check.
- Do not add a segment-relative checksum or any format change.
