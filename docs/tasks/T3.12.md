# T3.12: fsync the old segment in roll(), in every sync mode

Planner: Claude, read-only. Based on `internal/storage/wal.go` at 6018e7b. Branch: `fix/t3-12-roll-sync`.
**Depends on T3.8 (faultfs)**, hence T3.6 and T3.7. Red commit first, then the fix, as separate commits.
Split out of T3.10, which now covers only `TruncateBefore`.

## Goal
`roll()` (`wal.go:291-316`) creates the next segment, syncs the directory (`:300`), then closes the previous active segment
without an `fsync` (`:305-310`). Under `SyncNever` the old segment's tail is still unsynced. Power loss can keep the new
segment's directory entry (and possibly some of its data) while the old segment loses its tail. The old segment is then not the
last one, so a torn tail there is `ErrCorruptWAL` (`wal.go:196-199`) and the node refuses to start. Sync the old segment before
the new one becomes visible, in all sync modes.

## Invariants touched (RUNBOOK §7 refs)
§7.3 #4 (a crash at any write boundary leaves a recoverable state); §7.3 #2 (only the **last** segment may have a torn tail; this
change keeps older segments complete); §7.2 item 1 for `SyncAlways` is already met per write, so the added sync is redundant there.

## Behavior specification
- In `roll`, before `OpenFile` of the new segment (so the old data is durable before the new name exists), call `w.active.Sync()`
  when `w.active != nil`. Then create the new segment, `SyncDir`, close the old file. Failure of the sync returns the error and
  creates nothing; with T3.9 merged it also poisons the WAL.
- Applies in every mode. Under `SyncAlways` the data is already synced by `write`, so the call is a cheap no-op fsync; the executor
  may skip it when `w.policy == SyncAlways` provided the tests below pass (OPEN QUESTIONS 1).
- Cost: one fsync per segment roll (default every 16 MiB, `wal.go:36`).
- The first segment created by `Open` on an empty directory has no previous active file; no sync there.
- `Close()` keeps its own sync (`wal.go:483`). No change to `TruncateBefore` (T3.10) or to replay (T3.7).

## Implementation notes
- Cite RUNBOOK §7.3 in the comment; no protocol rule changes, so no paper section is needed.
- Keep the order sync(old), create(new), SyncDir, close(old). Do not move the directory sync.
- `maybeRoll` (`wal.go:410-416`) is called after the write, so the unsynced bytes it would cover are exactly the ones this protects.
