# D9: ops tooling (rolling update, pause, teardown guide) and docs/OPS.md
Depends on merged D1-D4 (`infra/README.md`, `infra/modules/compute`, `infra/scripts/*`) and D3 (`scripts/release*.sh`). The executor WRITES and tests with STUBS only; it never runs a script against AWS, never runs `terraform apply|destroy`, creates no IAM users or keys (CLAUDE.md; RUNBOOK §2.8-2.9). The HUMAN runs everything here. Cards D5/D5b/D7 may be unmerged: `docs/gateway.md` and `docs/web.md` are on main and are cited as is.

## Goal
Three human-run scripts plus `docs/OPS.md`: `scripts/rolling-update.sh` (binary update or restart, one node at a time, leader last, health-gated, abort-safe, idempotent, `--dry-run`), `scripts/demo-pause.sh` (stop/start instances), `scripts/demo-down.sh` (PRINTS the teardown order and checks preconditions, never destroys), and incident notes. Needed because `aws_instance.node` has `ignore_changes=[ami,user_data]` (`infra/modules/compute/nodes.tf:68`), so `terraform apply` never updates a node binary or unit; only this script does.

## Invariants touched
None of RUNBOOK §7 is changed. §7.3 is preserved: a restart reuses the WAL on the data volume (`nodes.tf:7-16`, `userdata-node.sh.tftpl:26-28`); nothing here replaces an instance (a replacement wipes WAL and vote, `nodes.tf:3`). Quorum rule: never two nodes down at once (RUNBOOK §10.8).

## Design decisions (each needs human sign-off, see OPEN QUESTIONS)
- **Path to the nodes.** Only EICE ssh: `aws ec2-instance-connect ssh --instance-id I --os-user ec2-user --connection-type eice -- "<cmd>"`, the form of `push-node-tokens.sh:60-62` (its caveat stands: remote command and stdin behaviour is unverified, `infra/README.md:100-101`). Needs `ssh_debug=true` (network default true, `variables.tf:51-55`).
- **How it learns the leader.** `raftkvctl` is NOT usable: the release builds only `raftkv-server` and `gateway` (`scripts/release.sh:65-66`), port 7000 accepts only `sg_nodes` and `sg_gateway` (`README:154-155`), `sg_eice` egress is tcp 22 only (`README:167`, so no `open-tunnel` to 7000), and the gateway has no ssh (`README:174`). Chosen: on each node, over EICE, `curl -fsS http://127.0.0.1:2112/health`, which prints `{"id","state","term","leader","commit","applied"}` (`cmd/raftkv-server/main.go:439-447`; state strings `Leader`/`Follower`/`Candidate`, `internal/raft/types.go:25-37`). `--metrics-listen :2112` is on in the unit (`raftkvd.service.tftpl:30`). Unverified: `curl` present on AL2023 (D8 checks; if absent use `python3` or bash `/dev/tcp`; the card's executor picks after OQ 2). One ssh per node per poll, not parallel.
- **Binary delivery.** Node role has `s3:GetObject` on `artifacts/raftkvd/*` only (`iam.tf:36-43`, `data.tf:54`) and reaches S3 via the gateway endpoint (no NAT). Key `artifacts/raftkvd/<v>/raftkv-server-linux-arm64` (`data.tf:58`, `release-upload.sh:41-47`). No `s3:ListBucket`, so a missing key shows as 403, not 404: the error text says "missing or not uploaded".
- **Hash.** Taken from the HUMAN's local `dist/<v>/MANIFEST` (`sha256.raftkv-server-linux-arm64=`, `release.sh:80`) after checks (`dirty=false`, `.sha256` agrees, version has no `/`), and checked ON the node with `sha256sum -c` (as user-data does, `userdata-node.sh.tftpl:38`), never from a hash found only in the bucket. The bucket `MANIFEST` is also fetched and compared (cross-check against a wrong dist dir).
- **Flow.** Preflight (read only, all 3 nodes): all reachable, each `/health` id equals its slot, exactly one Leader, no node lagging more than `--max-lag` (default 5) or refuse (exit 1, zero writes). Phase A, stage: on every node download to a temp file and verify (no service touched; any failure exits 2 with the cluster unchanged). Phase B, per node: order is recomputed each step from live `/health`: non-leaders first (ascending id), the leader last; skip a node whose `sha256sum /usr/local/bin/raftkvd` already equals the target (idempotent); re-check the other two are healthy; `cp -p` live binary to `raftkvd.prev`; `mv` staged file over it; `sudo systemctl restart raftkvd`; poll (2 s, default 180 s) until this node is Follower or Leader with a known leader and `applied` within N of the leader's. Strictly sequential, never backgrounded.
- **Failure.** Node k fails health: restore `.prev`, restart, wait for health (exit 3, cluster as before for node k; nodes before k stay on the new binary: a mixed state is normal for a rolling update, and rerunning with the OLD `dist/` dir is the downgrade, the same idempotent script). Rollback itself fails: exit 4 "MANUAL", nothing else touched. Later nodes are never touched after a failure.
- **`--restart-only`**: same loop and gates without stage or swap (token rotation, config you edited by hand). **`--dry-run`**: preflight reads, then prints order and the exact remote commands; no write command is issued. Config or unit-file changes are NOT pushed by v1 (OQ 3).
- **Gateway update path (no script).** The gateway has no ssh (`README:174`), its role has no SSM session rights (`iam.tf:64-86`), so a script cannot reach it. Its user-data change replaces the instance (`gateway.tf:57`); volume (registry, autocert cache) and Elastic IP are kept (`README:109-110,219`). Path: human bumps `release_version` and `release_sha256` in tfvars, `terraform plan`, read, `check.sh`, `apply` (the flip documented for `tls_staging`). Expect a few minutes of outage; the dashboard falls back to replay. Boot refetches both tokens (`gateway.service.tftpl:19`). Then the same tfvars bump keeps a later node replacement from installing an older binary.
- **Race.** The public chaos button could take a node down during an update (gateway rule is one node, `docs/gateway.md:189-192`; plus ours = two). Mitigation: preflight requires `GET <gateway>/v1/cluster` not `recovering` when `--gateway-url` is given (public read, 1 Hz cache, `docs/gateway.md:104`; idle spelling unverified); the per-node re-check before each restart; residual window of seconds is documented in OPS.md (availability only, WAL is fsynced).

## demo-pause.sh and demo-down.sh
- `demo-pause.sh pause|resume [--dry-run] <gateway id> <node1> <node2> <node3>`; same refusals as `push-node-tokens.sh:30-44` (profile, no static keys, CI, id format). pause: stop the gateway first, then the nodes (`aws ec2 stop-instances`, wait stopped); resume: start the nodes, `aws ec2 wait instance-status-ok`, then the gateway (its safe start heals nodes and holds the chaos slot until all 3 answer `Status`, `docs/gateway.md:242`). Never terminate or modify. Prints the billing note: stopped means no compute charge; still billing: the Elastic IP (about $3.65/mo, RUNBOOK §10.2) and EBS, 4 x 8 + 3 x 4 + 2 = 46 GiB gp3 (about $3.7/mo at $0.08, unverified price), S3 pennies.
- **Tokens survive a stop (verifiable from the module).** Node token files live in `/etc/raftkv` on the root volume (`userdata-node.sh.tftpl:33`; only `/var/lib/raftkv` is the data mount, `:26-28`), a stop keeps EBS, the unit is `enable`d (`:47`) and `ConditionPathExists` is then satisfied; private IPs are fixed (`nodes.tf`, `private_ip`). So NO `push-node-tokens.sh` on resume. Gateway tokens are refetched on every start. A stopped-then-started instance keeps its id; a REPLACED one needs the push (`README:88-90`). Data-volume remount on boot is by UUID with `nofail` (`:27`) and the unit `RequiresMountsFor` it: D8 confirms the first resume (unverified).
- `demo-down.sh --state-bucket B --artifacts-bucket B2 --domain D` (profile required). **Decision: it never calls `terraform` at all.** Reasons: RUNBOOK §2.9 and CLAUDE.md forbid agents running destroy, and a script an agent wrote and tested only with stubs should not own an irreversible destroy; the plan must be read as with apply (`README:79-83`); a wrong directory or profile destroys the wrong stack; bucket emptying and DNS are manual anyway. It runs read-only AWS checks (`sts get-caller-identity`, `s3api list-object-versions --max-items 1` per bucket, `ssm describe-parameters` for the three names; never `get-parameter`, never `--with-decryption`) and prints, in order: 1 `terraform destroy` in `infra/envs/demo`; 2 empty both buckets including versions and delete markers (state bucket only after step 1); 3 `terraform destroy` in `infra/bootstrap` (local state file kept until now); 4 delete the three parameters; 5 delete the DNS A record for `api.<domain>` (a dangling record is a takeover risk); 6 leave the dashboard in replay and update the README (RUNBOOK §10.9). Each step shows live status ("N object versions remain"). Exit 0 always except refusals.

## docs/OPS.md (sections; every command shown must exist; no real ids, tokens or domain secrets)
Node down (EICE: `systemctl status raftkvd`, `journalctl -u raftkvd`; `RestartSec=8` is the designed downtime, `raftkvd.service.tftpl:32-33`; a node with no token files is skipped, not failed: re-push). Leader flapping (`CPUCreditBalance`, `standard` credits throttle; election 1.0-1.9 s, `README:254-257`; D8 unverified). Gateway unreachable (no shell: `describe-instance-status`, `get-console-output`, `curl /healthz`, DNS; fix is the tfvars apply above; replay mode keeps the demo link alive, `docs/web.md:18-19`). Certificate renewal (autocert on 443 TLS-ALPN, cache `/var/lib/raftkv-gateway/autocert`, `docs/gateway.md:83-84`; causes: DNS or 443 blocked, `--tls-staging` left on, cache perms refused, Let's Encrypt limits, renewal window about 30 days before expiry: unverified; fix: check name, restart via reboot). Token rotation (three SSM names, put from a 0600 file as `README:57-64`; `push-node-tokens.sh` only `systemctl start`s, a no-op on a running unit (`:70`), so rotation = push, then `rolling-update.sh --restart-only`, then reboot the gateway (it refetches); node re-reading a changed token file without restart is unverified). Cost alarms (budget alerts at 20/30/40 actual, credits excluded, `README:288`; $20 look at Cost Explorer by usage type; $30 `demo-pause.sh pause` and investigate: NAT, extra EIP, unlimited credits, S3 versions; $40 ceiling: pause now, then `demo-down.sh` if unexplained). Stuck chaos slot (`chaos.state:"recovering"` until all 3 nodes answer Status, `docs/gateway.md:191-196`; heal is public; a gateway reboot safe-starts). Backups: there are none (no snapshot or backup resource under `infra/`, verified by grep; the 3 WALs are the only copies, EBS is not snapshotted, S3 versions cover release artifacts only; the keyspace is a demo that resets).

## Tests to write FIRST (red against stubs)
Library `scripts/ops_testlib.sh` sources `infra/scripts/_testlib.sh` (pass/fail/expect_ok, canary tokens `TOK_*`, `no_secret_anywhere`) and builds its own sandbox: STUB `aws` (logs argv per line, never env values), STUB `sleep`, `ssh`/`scp`/`terraform` as FORBIDDEN loggers, all first on PATH, no real binary reachable. The stub `aws ec2-instance-connect ssh` does NOT execute the remote command: it logs `remote(<id>): <cmd>` and answers from a small cluster model in `$sb/cluster/` (per node: binary sha, up, state, applied, leader id). Knobs: `STUB_LEADER=n`, `STUB_FAIL_SHA|S3|UNHEALTHY|ROLLBACK=n`, `STUB_DOWN_POLLS`, `STUB_LEADER_MOVES`, `STUB_DEGRADED=n`, `STUB_WRONG_ID`. On every `restart`/`stop` it counts non-healthy nodes and writes `two-down` to `$sb/violations`. Polling timeouts are short env overrides for tests only, never changed in assertions.
`scripts/rolling-update_test.sh`: order for leader 1, 2, 3 (leader last, others ascending); all 3 stages before the first `systemctl`; `violations` empty in every scenario; hash mismatch on node 2 exits 2 with zero `systemctl` or `mv`; S3 failure message; node never healthy: `.prev` restored, restart, exit 3, later nodes absent from the log; rollback fails: exit 4, nothing after; degraded preflight (node down, no leader, lag > N): REFUSED, zero write commands; leadership moves mid-run: order recomputed, still leader last, still never two down; rerun after success: no write command, exit 0; rerun after an abort at node 3 touches only node 3; `--dry-run`: no `s3 cp`, `mv`, `cp`, `systemctl` in the log, plan printed; `--restart-only`: no s3, same order; refusals each with the literal `REFUSED:` and zero aws calls (no profile, static key, CI, ids not 3 or malformed or duplicate, missing or dirty or inconsistent dist, bad bucket, node id differs from its slot); no `.token` path, `ssm`, or `TOK_*` in any logged line or output; only `ec2-instance-connect ssh --connection-type eice` is used; no `set -x`.
`scripts/demo-pause_test.sh`: pause stops the gateway then nodes, resume starts nodes, waits, then gateway; no `terminate`, `modify`, `push-node-tokens`; `--dry-run` issues no stop or start; refusals; billing text names the Elastic IP and EBS.
`scripts/demo-down_test.sh`: `terraform` stub never called; only allowed read verbs appear (`sts`, `s3api list-object-versions`, `ssm describe-parameters`), no `delete`, `rm`, `put`, `--with-decryption`; printed steps appear in the order above; exit 0 with non-empty buckets; refusals; static grep that no `scripts/*.sh` line executes `terraform apply|destroy`.
`scripts/ops-doc_test.sh`: OPS.md has the 8 headings and the word "no backups", mentions only scripts that exist, contains no 40+ char secret-like literal.
Each stub script is an executable that prints `not implemented` and exits 64, so tests fail on assertions (refusal tests also require the `REFUSED:` text), not on a missing file.

## OPEN QUESTIONS for the human
1. RUNBOOK §10.9 says `demo-down.sh` is "full destroy". Rule 2.9 forbids agents running it, not you. Accept print-only (recommended) or amend the runbook to let the script run `terraform destroy` after a typed confirmation?
2. Leader and lag come from node-local `/health` over EICE (one ssh per node per poll; `curl` on AL2023 unverified). Accept, or want the gateway `/v1/cluster` as the primary source (no ssh, but 1 Hz cache and needs the gateway up)? `--gateway-url` is optional either way.
3. Binary only in v1; unit or flag edits stay manual (OPS.md lists the same one-node-at-a-time steps). Want a `--unit-file` mode in a D9b card?
4. Failure policy: roll back only the node in flight (recommended; downgrade = rerun with the old dist) or also revert already-updated nodes?
5. The public chaos button can overlap an update (two nodes down briefly, availability only). Accept the documented window, or add a gateway maintenance switch (gateway change, separate card)?
6. Default `--max-lag 5` and a 180 s per-node timeout: fine? Is wire compatibility between adjacent releases during the mixed window guaranteed (unverified; proto changes)?
7. Gateway update by tfvars bump and `terraform apply` (outage of minutes), no script: acceptable?
