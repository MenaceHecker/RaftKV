## Goal
`Open` makes the `wal` directory with `MkdirAll` (`wal.go:101`), `NewSnapshotter` makes `snap` (`snapshot.go:41`), and `lockDir` makes the
data directory (`lock_unix.go:19`). Nothing ever syncs the **parent** that names them: `roll`'s `syncDir(w.dir)` (`wal.go:300`) and
`Save`'s `syncDir(s.dir)` (`snapshot.go:133`) sync the *contents* of `wal` and `snap`. After power loss on a node's first start the
whole `wal` or `snap` directory can disappear while every file inside it was fsynced. Sync each new directory's parent, and its new
ancestors' parents.

## Why this is a safety problem (the window is a node's first start)
- Election Safety (Raft §5.2, Figure 2 persistent state): A and B vote for A in term 1; A leads. B loses power; its unsynced entry for
  `wal` disappears despite the vote record's fsync. B restarts with an empty HardState and grants C a term-1 vote; C plus B elect C
  while A remains a term-1 leader. Two leaders in one term.
- Snapshots: the first `CreateSnapshot` (`disk.go:257-275`) saves into `snap`, records the meta in the WAL and then deletes WAL
  prefix segments (`TruncateBefore`). If `snap`'s own entry is not durable, power loss loses the snapshot while the WAL prefix is gone;
  the next open fails with `ErrCorruptWAL` (`disk.go:85-91`) or loses acked state.
- The window closes only if some later action happens to sync the parent. Nothing in the code does.

## Behavior specification (decided)
- One helper `mkdirAllDurable(fsys FS, dir string) error` in `internal/storage/fs.go` (or `mkdir.go`). Steps: `MkdirAll(dir)`, then for
  **every component of the path** `SyncDir(parent(component))`, outermost first, then `SyncDir(dir)`. The sync is unconditional, not only
  for components this call created: an earlier run may have created entries and died (process crash) before they were synced, so the
  next run sees them existing and would otherwise skip the barrier. Cost: a few directory fsyncs at open, never on the hot path.
- Used by: `Open` (`wal.go:101`), `NewSnapshotter` (`snapshot.go:41`) and `FS.Lock` / `lockDir` (`lock_unix.go:19`). `OpenDiskStorage`
  keeps its order (lock, snapshotter, WAL). Idempotent.
- Errors wrap the existing messages. **Any directory sync failure fails startup (decided), including on pre-existing ancestors.** The
  sync is the only barrier for entries an earlier process may have created and not synced, so ignoring a failure would let the node ack
  a vote whose directory chain can still vanish (a previous process created `/data/a/b/node1` and died before `/data` was synced; an
  ignored `SyncDir(/data)` error would still let the node ack, and power loss then removes `a` and the vote). Relative paths work
  (`data/wal`, parent `.`). `SyncDir` of `/` or a mount point must succeed on supported platforms; where a filesystem rejects
  directory fsync (some FUSE or network mounts) startup fails, which is accepted.
