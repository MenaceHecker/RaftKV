## Goal
Give an operator and the demo gateway a control surface on each node: read status, crash it, pause it, partition it, add network loss and
delay, and watch a stream of state-change events. Faults are applied in a wrapper around `node.Transport`, so they are application-level;
the docs must say so (RUNBOOK §10.5). Nothing here may change Raft behaviour when no fault is set.

## Invariants touched
RUNBOOK §7.1 and §7.2 are **not** changed; the wrapper only drops or delays messages, which Raft already tolerates (a lost or late message
is indistinguishable from a network fault). `internal/raft` is not edited. §2: no `time.Now`/`math/rand` in `internal/raft` (unaffected);
the wrapper lives in `internal/transport` and takes an injected clock and rand for tests.

## Facts from the code (at a632530)
- `node.Transport` is one method, `Send([]raft.Message)` (`internal/node/node.go:27`). `PeerTransport.Send` (`transport/peer.go:196`) delivers
  to self directly and queues for peers. Wrapping the outbound side is one decorator, but a **one-way** partition also needs an inbound
  filter in `RaftServer.Deliver` (`peer.go:352`); outbound-only blocking cannot stop a peer from sending to this node.
- `Status` already exists on `KVService` (`raftkv.proto:82`, fields `node_id, leader_id, leader_address, term, state, commit_index,
  applied_index`). `node.Status` (`node.go:107`) also has `Members` and `SnapshotsReceived`.
- Events source: `Recorder.LeaderChanged(term, leader, isLeader)` (`node/metrics.go`, fired from `observeLeadership`, `node.go:780`) and
  `SnapshotCreated`/`SnapshotReceived`. There is **no** hook for commit/applied movement, role changes other than via leader change, or
  elections starting. Candidate/pre-candidate transitions are not observable from `internal/node` today.
- `cmd/raftkv-server` serves Raft, KV and Cluster on **one** `--listen` gRPC port plus `--metrics-listen` (`main.go:171-173`).
  `ClusterService` (AddNode/RemoveNode/ListMembers) is registered there too.
- The process has no restart supervisor; the runbook's `Restart=always`, `RestartSec=8` (§10.5) comes from systemd.

## Implementation notes
- Messages dropped by the wrapper are lost, never reordered into a different term; do not touch `raft.Message` contents.
- Delay must not block `Send`: hand delayed messages to a per-peer goroutine fed by the clock, preserving order per peer.
- `Pause` must stop ticking, not just messages, or the node campaigns on resume; use the node's tick source (`TickInterval`) with a
  paused gate, and say so in the doc. This is the only change in the run loop's behaviour and is off by default.
- Events are emitted after state is observed in the run loop, so the stream never shows a state the node did not hold.
- Admin calls need no auth in-process; reachability is the control (security groups, RUNBOOK §10.4). Do not log request payloads.

## OPEN QUESTIONS for the human
1. **Port.** The runbook says admin on `:9000`; CLAUDE.md says the server takes one `--listen` plus `--metrics-listen`. Add a third
   `--admin-listen` flag (card assumes yes), or serve admin on the existing port? The latter fails "callable only on :9000".
2. **`Crash(restartDelay)`.** The process cannot restart itself and `RestartSec` is fixed in systemd. Should `restartDelay` be ignored
   (documented as a hint), or should `Crash` spawn a supervisor-less re-exec? The card assumes ignored, with `os.Exit(137)`.
3. **Status.** Reuse `KVService.Status` fields in `AdminService.Status` (card assumes yes, plus `members`, `joint`), or leave the admin
   one minimal?
4. **Election events.** "Elections" cannot be observed from `internal/node` without a raft-core hook (candidate transitions). Add a small
   observer interface in `internal/raft` (needs human raft-core review), or derive "election" from term bumps (card assumes derived)?
5. **Pause semantics.** Gate ticks (card assumes) or also stop applying committed entries?
