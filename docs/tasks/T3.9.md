# T3.9: poison the WAL on the first write or sync error; the node must stop

Planner: Claude, read-only. Based on `internal/storage` and `internal/node` at 6018e7b. Branch: `fix/t3-9-poison-wal`.
**Depends on T3.8 (faultfs)**, and so on T3.6 and T3.7. Red commit first, then the fix, as separate commits.

## Goal
After the first failed `Write`, `Sync`, roll or directory sync, the WAL refuses every later write and the node exits non-zero
instead of continuing. Today `write` (`wal.go:395-408`) returns the error and leaves the WAL usable.

## Why (fsyncgate reasoning)
- After a failed `fsync` the kernel may mark the dirty pages clean or drop them. A retry can return success for data that never
  reached disk (PostgreSQL "fsyncgate", 2018; Linux reports the error once per descriptor). Retrying is unsafe; the only safe
  recovery is to stop and rebuild state from what is durable on restart.
- A failed or short `Write` leaves partial bytes in the file (`wal.go:396-400` adds `n` to `activeSize` and returns). A later
  append then lands after that garbage. After T3.7, a bad record followed by valid records is mid-log damage: the node refuses to
  start (`ErrCorruptWAL`). So continuing turns a transient error into a bricked data directory.
- Raft only requires that the node not ack what is not durable. Stopping is always safe (crash-stop is in the failure model).

## Invariants touched (RUNBOOK §7 refs)
§7.2 item 1 (persist before reply; a failed persist must not be followed by a reply that assumes it) and §7.3 #3, #4.

## What exists already (checked in code)
- Core marks storage failures `ErrStorage` (`internal/raft/log.go:71,101`; `node.go:508`; `snapshot.go:77`). `internal/node` treats it as
  fatal in step, tick and proposal paths (`node.go:376,454,644`), stops the loop (`donec` closes) and `cmd/raftkv-server/main.go:194-200`
  returns an error, so `main` exits 1 (`main.go:30-33`). The server therefore already stops on those paths.
- **Gaps:** `maybeSnapshot` swallows `CreateSnapshot` errors (`node.go:707-715`), and `compact` returns them to a caller
  (`node.go:693-695`) without marking them fatal. A failing WAL write inside `CreateSnapshot` (meta record `disk.go:261`, HardState
  re-record `wal.go:440`) is therefore silent, and the next append proceeds on a broken WAL.

## Behavior specification
- `WAL` gets `failed error`. First error from `write` (Write or Sync), from `roll` (create, dir sync, close) after bytes were written,
  from `TruncateBefore`'s writes or removes, and from `Sync()`/`Close()` sets it.
  Every later `AppendEntries`, `SaveHardState`, `SaveSnapshotMeta`, `TruncateBefore`, `Sync` returns `ErrWALFailed` wrapping the cause
  (`errors.Is` works for both). `Close` closes the descriptor, does not call `Sync`, and returns the cause.
- `DiskStorage` returns errors from the WAL unchanged and never updates memory on failure (already true at `disk.go:145-148,229-234`).
- `internal/node`: `fatal(err)` (`node.go:554`) also matches `storage.ErrWALFailed`; `maybeSnapshot` and `compact` call a common
  `n.fail(err)` that closes the loop like the other fatal paths. No `os.Exit` in the library; the process exit stays in `main`.
- A failed snapshot **file** write (`snapshot.go:Save`) is not a WAL failure: it aborts that snapshot, removes the temp file and the
  WAL stays usable. Only the WAL poisons. Document with a test.
