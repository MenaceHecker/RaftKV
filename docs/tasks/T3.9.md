# T3.9: poison the WAL on the first write or sync error; the node must stop

Planner: Claude, read-only. Based on `internal/storage` and `internal/node` at 6018e7b. Branch: `fix/t3-9-poison-wal`.
Execution order (all cards): **T3.6, T3.7, T3.8, T3.11, T3.13, T3.9, T3.10, T3.12, T3.14, T3.15.**
**Depends on T3.8 (faultfs)**, and so on T3.6 and T3.7. Blocks T3.15. Red commit first, then the fix, as separate commits.

## Goal
After the first failed `Write`, `Sync`, roll or directory sync, the WAL refuses every later write and the node exits non-zero
instead of continuing. Today `write` (`wal.go:395-408`) returns the error and leaves the WAL usable.

## Why (fsyncgate reasoning)
- After a failed `fsync` the kernel may mark the dirty pages clean or drop them. A retry can return success for data that never
  reached disk (PostgreSQL "fsyncgate", 2018; Linux reports the error once per descriptor). Retrying is unsafe; the only safe
  recovery is to stop and rebuild state from what is durable on restart.
- A failed `Write` can leave partial bytes (`wal.go:396-400` adds `n` to `activeSize` and returns when `err != nil`). `os.File.Write`
  already returns a non-nil error whenever `n < len(buf)` (io.Writer contract), so the real-OS path detects short writes; only a fake
  can violate this, which is why faultfs `ShortWrite(k)` must return an error (T3.8). A later append lands after the garbage. After
  T3.7, a bad record followed by valid records is mid-log damage: the node refuses to start (`ErrCorruptWAL`). Continuing turns a
  transient error into a bricked data directory.
- Raft only requires that the node not ack what is not durable. Stopping is always safe (crash-stop is in the failure model).

## What exists already (checked in code)
- Core marks storage failures `ErrStorage` (`internal/raft/log.go:71,101`; `snapshot.go:77`). `internal/node` treats it as fatal in step,
  tick and proposal paths (`node.go:376,454,644`; `fatal` is `:554`), stops the loop (`donec` closes), and
  `cmd/raftkv-server/main.go:194-200` returns an error, so `main` exits 1 (`main.go:29-33`). **A WAL failure inside an Append already
  stops the node today**, so `TestNodeStopsWhenTheWALFails`-style tests on that path pass before the fix.
- **Gaps:** `maybeSnapshot` swallows `CreateSnapshot` errors (`node.go:713-715`; called at `:544`), and `compact` returns them
  (`node.go:694-696`, replied at `:396`) without marking them fatal. A failing WAL write inside `CreateSnapshot` (meta record
  `disk.go:261`, HardState re-record `wal.go:440`) is therefore silent, and the next append proceeds on a broken WAL.

## Behavior specification
- `WAL` gets `failed error`. First error from `write` (Write or Sync), from `roll` (create, dir sync, close) after bytes were written,
  from `TruncateBefore`'s writes, `Remove`s (`wal.go:459`) or `SyncDir` (`:463`), and from `Sync()`/`Close()` sets it.
  Every later `AppendEntries`, `SaveHardState`, `SaveSnapshotMeta`, `TruncateBefore`, `Sync` returns `ErrWALFailed` wrapping the cause
  (`errors.Is` works for both). `Close` closes the descriptor, does not call `Sync`, and returns the cause.
- **Memory vs disk, narrowed.** "Memory is not updated on failure" holds only for `SetHardState` (`disk.go:145-148`) and `Append`
  (`:229-235`) at the `DiskStorage` level. It is **false** for `CreateSnapshot` (`s.entries` compacted at `:269`, `TruncateBefore`
  fails at `:271`, purge at `:275`) and `ApplySnapshot` (`s.entries` replaced at `:325`, `TruncateBefore` at `:327`, purge `:330`).
  Inside the WAL, `lastIndex` (`wal.go:359`) and `hardState` (`:376`) are set before a failing `maybeRoll`. Behavior is pinned by the
  tests below; the ordering itself is T3.15.
- `internal/node`: `fatal(err)` (`node.go:554`) also matches `storage.ErrWALFailed`; `maybeSnapshot` and `compact` call a common
  `n.fail(err)` that closes the loop like the other fatal paths, for **any** `CreateSnapshot` error (conservative; whether purge
  failures may be non-fatal is T3.15). No `os.Exit` in the library; the process exit stays in `main`.
- A failed snapshot **file** write (`snapshot.go:Save`) is not a WAL failure: it aborts that snapshot, removes the temp file and the
  WAL stays usable. Only the WAL poisons. Document with a test.

## Tests to write FIRST
Faults are **one-shot and recoverable** (`Rule{Nth: 1}`, T3.8): the next call would succeed, so only the code under test can refuse
it. A `CrashAt` simulator fails every later op itself and cannot prove poisoning. Red = fails on current code.
1. **Red** `TestWriteFailurePoisonsTheWAL`: one-shot `ErrSync` on the first sync: `AppendEntries` fails; the next `AppendEntries`,
   `SaveHardState` and `TruncateBefore` return `errors.Is(err, ErrWALFailed)`. (Today they succeed.)
2. **Red** `TestShortWriteThenRetryDoesNotBrickTheDirectory`: one-shot `ShortWrite(5)` on append, caller retries. After the fix the retry
   is refused and a reopen succeeds with the pre-failure entries. Before the fix the retry succeeds and the reopen returns
   `ErrCorruptWAL` (mid-log form, needs T3.7).
3. **Red** `TestSyncFailureOnRollPoisons` and `TestSyncFailureInTruncateBeforePoisons`: one test per op in `TruncateBefore` (HardState
   write; `Remove` `:459`; `SyncDir` `:463`) and ENOSPC on roll create.
4. **Red** `TestEveryFailureAfterPoisonKeepsDurableStateIntact`: for each op index of T3.8 test 3, inject a **one-shot** error at that
   op (not `CrashAt`), issue a further write (expected: refused), then `Crash()`, reopen: the T3.8 checker passes.
5. **Control** `TestSnapshotFileFailureDoesNotPoisonTheWAL` (green today and after; guards the spec).
6. **Red (the meaningful node test)** `TestFailedSnapshotWriteStopsTheNode` (`internal/node`, `Config.FS` = faultfs): arm a one-shot
   failure on the meta record write inside `CreateSnapshot`; the `maybeSnapshot` path stops the node (`Done()` closes, `Stop()`
   returns, no later proposal acked). Today `maybeSnapshot` returns silently and the node keeps running.
7. **Control** `TestNodeStopsWhenTheWALFails`: one-shot `ErrSync` armed after the cluster is up: a proposal returns an error, `Done()`
   closes, `Stop()` returns without hanging, **no later proposal is acked**. Passes today (Append errors are already `ErrStorage`).
8. **Red** `TestSnapshotCleanupFailuresAreReportedAndStopTheNode`: one-shot failures at each of: `TruncateBefore` `Remove` (`wal.go:459`),
   its `SyncDir` (`:463`), purge `Remove` (`snapshot.go:344`), purge `SyncDir` (`:348`). For each, assert: `CreateSnapshot` returns the
   error; `DiskStorage` memory (`SnapshotMeta()`, `LastIndex`) and the reopened disk state agree (snapshot published, so the
   reopened store is at the new snapshot, as is memory, per `disk.go:269`); WAL-side failures poison; the node stops. Separately a
   failure **before publication** (snapshot file write) leaves memory unchanged. Same table for `ApplySnapshot` (`disk.go:325-330`).
9. `TestChaosDiskFaultStopsOnlyThatNode` (chaos package, optional): one node's FS fails; the other two keep a quorum and the history
   stays linearizable. If infrastructure is missing, list in the report instead (OPEN QUESTIONS 1).
