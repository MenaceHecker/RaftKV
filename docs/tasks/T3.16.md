## Goal
`ProposeConfChange` (`internal/raft/confchange.go:5`) refuses only on `inJoint()` (`:11,14`); it never asks whether a config entry is still
uncommitted. Raft allows at most one pending configuration change (dissertation §4.1, §4.3; paper §6). **Severity, stated plainly:**
no client can create a configuration entry or send `Leave`. `internal/node` exposes only `AddNode`/`RemoveNode` (`node.go:606,615`), the gRPC
admin service the same (`transport/kvserver.go:175,189`). `Node.Step` is public in-process (`node.go:261`) and `raft.Step` keeps the entry
types of a `MsgPropose` (`raft/node.go:341`, `replication.go:18-24`), but the network cannot deliver one: `RaftServer.Deliver` decodes
through `messageTypeFromWire` (`codec.go:47-71`), whose ten values exclude `MsgPropose`, `MsgCampaign` and `MsgReadIndex`
(`raftkv.proto:91-106`); pinned by `codec_test.go:125,197-217`. `EntryConfChange` does travel inside `MsgAppendRequest`
(`codec.go:152-175`), the follower path, unchanged here. The unsafe chain in test 7 therefore needs direct `raft.Node.ProposeConfChange`
calls (tests and the chaos harness). T3.16 (a) hardens the raft API and (b) closes the client-reachable gap: `AddNode` returns when the
joint entry commits, the automatic leave is appended in that same step, and a following `AddNode`/`RemoveNode` is accepted while that
leave is uncommitted. Nothing here claims a client-driven safety violation.

## Facts from the code (re-verified at 6d4496c)
- A config entry takes effect on **append** (`confchange.go:28-34`) and is re-derived from the log by `rebuildConfig` (`:62-103`).
  Quorums (`maybeCommit` `replication.go:215`, `commitReady` `membership.go:114`) use the in-effect `n.conf`, committed or not.
- The only pending-state field is `jointEntryIndex` (`node.go:125`): 0 after a leave. Nothing tracks an uncommitted leave, so once
  `Leave` is appended `inJoint()` is false and `Add`/`Remove` is accepted. That is the hole. No test reads the field (grep).
- `Leave` is accepted whenever `inJoint()` (`:11`), before the joint entry commits.
- `rebuildConfig` returns at `:68-71` for an empty suffix **before** `jointEntryIndex` is assigned (`:100`): stale after a snapshot install
  that discards the suffix. It also skips a config entry whose application fails (`:87-90`) without updating `jointAt`.
- `maybeFinishConfChange` (`:105-118`) returns when `jointEntryIndex == 0` (`:109`): a snapshot whose `Conf` is joint with no config entry in
  the suffix never auto-leaves (HYPOTHESIS, test 5c). Called from `replication.go:165` and `snapshot.go:118` only after `maybeCommit`.
- `becomeLeader` (`raft/node.go:474`) does not call `rebuildConfig`; pending state must already be derived. It calls `maybeCommit` (`:~500`) but
  never `maybeFinishConfChange`: a sole-voter-like joint initial configuration (for example an externally supplied `InitialConfState` {1}/{1}) commits
  its no-op inside `becomeLeader` and never reaches the automatic leave. See the backlog; the automatic-leave guarantee of rule 4 covers valid
  one-server transition configurations, whose no-op commits through the ack path.
- `rebuildConfig` starts from `baseConf`, which is stale after a local compaction; T3.17 fixes that first (snapshot-based base). The rules below
  assume the T3.17 base.
- Client entry: `internal/node/node.go:621,642-645`. gRPC mapping: `ErrConfChangeInFlight` -> `FailedPrecondition`, `ErrNotInJoint` ->
  `InvalidArgument` (`kvserver.go:112-118`).
- After the fix a manual `Leave` is effectively unreachable from a live leader: the commit that makes the joint entry committed runs
  `maybeFinishConfChange` in the same step. `ErrConfChangeInFlight` becomes a defensive branch (kept).

## Rule to implement (the contract the tests pin)
1. `rebuildConfig` derives `lastConfIndex`: index of the newest `EntryConfChange` in the log above the snapshot, **0 if none**, counting every
   decodable config entry including ones whose application is skipped. It is assigned **unconditionally before any return**, including the
   empty-suffix branch. Replaces `jointEntryIndex`. Recomputed on append, truncation, snapshot install and restart.
2. `pending() = lastConfIndex > CommitIndex()`.
3. `ProposeConfChange` check order: leader; **pending** -> `ErrConfChangePending` with message "configuration change at index N is pending;
   wait for it to commit, then retry"; **not committed in term** (`!hasCommittedInCurrentTerm()`, `readonly.go:111`) -> the same sentinel,
   message "this leader has not yet committed an entry in its term; retry shortly"; then the existing type checks (`ErrNotInJoint`,
   `ErrConfChangeInFlight`). Both messages wrap one sentinel (`fmt.Errorf("%w: ...")`) and are distinguishable. gRPC: `FailedPrecondition`
   with `err.Error()` as the message (explicit case before the InFlight case, `kvserver.go:112`); not `Unavailable`.
   `ErrConfChangePending` wraps `ErrConfChangeInFlight` (decided), so `errors.Is` holds for both and `TestOnlyOneChangeMayBeInFlight` is untouched.
4. `maybeFinishConfChange` predicate, separate from `pending()`: `state == Leader && conf.inJoint() && lastConfIndex <= committed &&
   hasCommittedInCurrentTerm()`, then propose `Leave`. The `jointEntryIndex == 0` guard is removed. It is not re-proposed while its own
   leave is uncommitted (the appended leave clears joint) and is retried after a leadership change. Scope: valid one-server transition
   configurations (a no-op commit that reaches this function through the ack path); a joint initial configuration that commits inside `becomeLeader`
   is backlog.
5. Followers, restart replay and snapshot install accept whatever the log holds. This is a leader proposal rule only.

## Existing tests that change (own commit, `tests-modified-reviewed`; passes on current code, lands BEFORE the core fix)
Five tests call `Leave` straight after `Add`/`Remove`. They encode the bug: they propose a leave before the joint entry commits. This is an
**intended spec change** (no test-only seam in production code); the one assertion lost in each is "a manual `Leave` right after `Add`/`Remove` returns nil".

Common facts. `leaderWithConfChange` calls `awaitLeader`, which ticks with `deliverAll`, so the leader's no-op is already committed (assert
`hasCommittedInCurrentTerm()` once in the edited tests). In a 3-node harness node 4 does not exist; `Add 4` commits with nodes 1,2,3 (3 of 4 incoming).
Inserting `c.deliverAll()` before a `Leave` therefore commits the joint entry; the automatic leave is appended synchronously inside the `Step` of the ack
that commits it (`replication.go:164-166`) and is itself committed before `deliverAll` quiesces. No partial delivery avoids this. The manual `Leave` then
returns `ErrNotInJoint` and the test's `t.Fatalf` fires. After the fix, a manual `Leave` straight after `Add` without `deliverAll` returns
`ErrConfChangePending`, which also fires the fatal. Either way the manual `Leave` must go.
