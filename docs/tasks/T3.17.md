# T3.17: a configuration must be derived from the snapshot base, and a snapshot's Conf must equal the configuration as of its index

Planner: Claude, read-only. Based on 6d4496c. Branches: `test/t3-17-snapshot-conf` (red tests), then `fix/t3-17-snapshot-conf-at-index`.
Found while verifying T3.16. Claims come from reading; **no test was run**. A review (Codex) found the stale-base defect in part 2 below; it is
a required fix, not a hypothesis.

## Goal
Two defects share one invariant, "the configuration as of an index is the snapshot's `Conf` plus the config entries above the snapshot":

1. **Stale `baseConf` in `rebuildConfig` (REQUIRED fix).** `Node.baseConf` is assigned only in `NewNode` (`raft/node.go:199`) and `restore`
   (`snapshot.go:84`). A snapshot the node creates itself (`storage.CreateSnapshot` from `internal/node`) never advances it. `rebuildConfig`
   (`confchange.go:63`) always starts from that stale base and replays only the log that is still stored, so config entries compacted away are lost.
2. **The snapshot writer stores the wrong Conf.** `compact` (`internal/node/node.go:~693`) and `maybeSnapshot` (`:~712`) pass `n.raft.ConfState()`,
   i.e. `n.conf.toState()` (`raft/confstate.go:38`), the append-effective configuration including config entries above `applied`, committed or not.

**Reachability of defect 1 in ordinary operation: yes, verified by reading.** No fault, restart or failure is needed:
`AddNode(4)` commits and its automatic `Leave` is appended and commits; the automatic snapshot (`maybeSnapshot`, fired from the apply loop
`node.go:~547` once `applied` passes `lastSnapshot + SnapshotThreshold`) compacts through both entries; the next `AddNode(5)` appends an entry,
`ProposeConfChange` calls `rebuildConfig` (`confchange.go:32`), which starts from the original {1,2,3} with the entries that added 4 gone, and derives
joint {1,2,3}/{1,2,3,5}. **Node 4 silently stops being a voter** and the quorum sets are wrong. A follower hits the same path when the entry
arrives (`replication.go:125`, `containsConfChange` or truncation). A restart with the production wiring is not affected by defect 1 alone,
because `internal/node/node.go:207-216` passes `snap.Conf` as `InitialConfState`; the raft-level `NewNode` over a snapshotted storage with `Peers`
only (the harness `restart`, `harness_test.go:215-237`) is.

**Reachability of defect 2:** an automatic snapshot while any `AddNode`/`RemoveNode` is pending above `applied`; normal operation reaches it.
`DiskStorage.CreateSnapshot` (`storage/disk.go:251`) and `MemoryStorage.CreateSnapshot` (`raft/storage.go:174`) store the Conf as given.

## Why defect 2 matters (consequences shown by reading; tests below)
1. If the pending entry `j` is later truncated, the durable snapshot still says "joint with the never-committed incoming set". Restart sets the base
   from `snap.Conf` and nothing in the log reverts it: wrong quorums. Example: joint {1,2,3}/{1,2,3,4} needs 3 of 4 incoming, so votes or matches from
   {1,2} satisfy the correct settled quorum and fail the reconstructed one. This establishes wrong quorum computation, not by itself conflicting commits.
2. If `j` survives, restart replays it on a base that is already joint; `enterJoint` fails with `ErrConfChangeInFlight` (`membership.go:61-62`),
   `rebuildConfig` skips it (`confchange.go:87-90`), the joint entry is not seen as pending and the leader never auto-leaves (`:109`).
3. `sendSnapshot` ships `storage.Snapshot()` unchanged, so a lagging follower adopts the same bad Conf when this node is leader.
**T3.11 restore assumptions:** T3.11's fixtures feed `restore` a snapshot whose `Conf` is the configuration at the snapshot index, which is correct;
the production writer does not guarantee it. T3.11's tests stay valid; none covers a snapshot made by `compact` while a config entry is pending
above `applied`, and none appends a config entry after a local compaction.

## Facts from the code (6d4496c)
- `MemoryStorage.Snapshot` (`raft/storage.go:169`) and `DiskStorage.Snapshot` (`storage/disk.go:301`) return `ErrSnapshotUnavailable` while no
  snapshot exists. `DiskStorage.Snapshot` loads the snapshot file including its data (`disk.go:306`): it must not run on every `rebuildConfig`.
- In production `NewNode` receives `snap.Conf` as `InitialConfState` (`internal/node/node.go:207-216`), so the "initial configuration" the raft node
  holds at construction is already the snapshot Conf when a snapshot exists. "No snapshot" is the only case where it is the original `Peers`.
- `storage.FirstIndex()` is the snapshot index plus one (`raftLog.firstIndex`, `log.go:22`).
- `compact` and `maybeSnapshot` return early when `applied <= lastSnapshot`, so they never ask for an index below the stored snapshot.

## Fix sketch (for the executor to confirm against the code)
- **Base.** The configuration base is "snapshot `Conf` at snapshot index `s`", or, with no stored snapshot (`errors.Is(err, ErrSnapshotUnavailable)`),
  the **initial configuration at index 0** (the config the node was constructed with; keep it as a separate immutable field). Any other
  `Snapshot()` error is propagated, never swallowed. `snap.Conf.IsEmpty()` falls back to the initial configuration.
- **Cheap refresh.** `rebuildConfig` must not call `storage.Snapshot()` each time (disk loads the data). Cache `baseConf` with its `baseIndex`; at
  the top of `rebuildConfig` compare `storage.FirstIndex()-1` with `baseIndex` and reload the base from `storage.Snapshot()` only when they differ
  (a local compaction or a restore moved it). `restore` and `NewNode` use the same helper. This replaces the stale assignments at `node.go:199` and
  `snapshot.go:84` and fixes defect 1 for the leader, follower, truncation and restart paths in one place. The executor may pick a different refresh
  mechanism if it keeps the same behaviour and cost.
- **`raft.Node.ConfStateAt(i Index) (ConfState, error)`**: base as above (index `s`), then replay config entries in `(s, i]` with the same loop as
  `rebuildConfig` (shared helper bounded by `i`, same decode and skip policy). `i == s` returns the base as is. `i < s` returns `ErrCompacted`
  (`storage.go:30`), never a guess. `i > LastIndex()` is rejected, no partial reconstruction. `compact` and `maybeSnapshot` pass `ConfStateAt(applied)`;
  if it ever errors the snapshot is skipped, not written with a wrong Conf. The node run loop serializes the lookup and snapshot creation.
- **The snapshot wire format and the stored `Snapshot` shape do not change**: only the value in the existing `Conf` field does.
- `CreateSnapshot` validation (reject a joint `Conf` with an empty `Incoming`) is out of scope.
