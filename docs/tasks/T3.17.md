# T3.17: a snapshot's Conf must equal the configuration as of its index

Planner: Claude, read-only. Based on 6d4496c. Branches: `test/t3-17-snapshot-conf` (red), then `fix/t3-17-snapshot-conf-at-index`. Found while verifying T3.16.
Claims come from reading; **no test was run**.

## Problem (verified in code, reproduction unrun)
`internal/node/node.go:693-697` (`compact`) and `:712-716` (`maybeSnapshot`) call `storage.CreateSnapshot(applied, data, n.raft.ConfState())`.
`ConfState()` is `n.conf.toState()` (`raft/confstate.go:38`): the **append-effective** configuration, which includes config entries above `applied`,
committed or not. A snapshot at index `a` can therefore carry a `Conf` that only exists because of an entry at `j > a` (possibly uncommitted).
`DiskStorage.CreateSnapshot` (`storage/disk.go:251`) and `MemoryStorage.CreateSnapshot` (`raft/storage.go:174`) store it as given.

**Reachability:** automatic snapshot while any `AddNode`/`RemoveNode` is pending above `applied`. `maybeSnapshot` fires from the apply loop
(`node.go:547`) once `applied` passes `lastSnapshot + SnapshotThreshold`, with no regard for a config entry in flight, so normal operation reaches it.

## Why it matters (hypotheses until red)
1. If entry `j` is later truncated, the durable snapshot still says "joint with the never-committed incoming set"; `restore`/restart sets
   `baseConf = snap.Conf` (`snapshot.go:83-85`, `node.go:207-216`) and nothing in the log reverts it: wrong quorums, a safety risk.
2. If `j` survives, restart replays it on a base that is already joint; `enterJoint` fails with `ErrConfChangeInFlight` (`membership.go:61-62`) and
   `rebuildConfig` skips it (`confchange.go:87-90`): the joint entry is not seen as pending and the leader never auto-leaves (`:109`).
3. `sendSnapshot` ships `storage.Snapshot()` unchanged, so a follower can adopt the same bad `Conf` and has no entry to revert it.
**T3.11 restore assumptions:** T3.11's fixtures (`docs/tasks/T3.11.md` 3e/3f) feed `restore` a snapshot whose `Conf` is the configuration at the snapshot
index, which is correct; the production writer does not guarantee it. The restore code is not wrong, its precondition is not enforced. T3.11's tests
stay valid; none covers a snapshot produced by `compact` while a config entry is pending above `applied`.

3. **Moved to the end of T3.16's commit plan (commit 10)**: entry survives and commits; after restart exactly one automatic leave and one pending index. It depends on T3.16 rule 1 and is not in this card.
4. Follower variant: follower with an uncommitted config entry compacts; leader later sends it a snapshot; `Conf` equals the config at that index.
5. Property: for random Add/Remove/compact/crash/truncate schedules, `snapshot.Conf` equals the config replayed from the log up to `snapshot.Index`.
6. HYPOTHESIS: commit an Add, compact past it, then force a truncation or config append; members must still include the added node (stale `baseConf`).
7. `ConfStateAt`: `i == s` returns the snapshot `Conf`; `i < s` returns `ErrCompacted`; `i` above `s` replays; the wire encoding of a snapshot is byte-identical before and after (golden).

## Fix sketch (for the executor to confirm against the code)
Add `raft.Node.ConfStateAt(i Index) (ConfState, error)`: take the base from `storage.Snapshot()` (its `Index` s and `Conf`, authoritative), then replay
config entries in `(s, i]` (same loop as `rebuildConfig`, bounded by `i`). **It cannot be computed from a log already compacted past `i`**: for `i < s`
the entries are gone and the base is the config at `s`, so it returns `ErrCompacted` (`storage.go:30`), never a guess; `i == s` returns the snapshot `Conf`
as is. `compact`/`maybeSnapshot` already return early when `applied <= lastSnapshot` (`node.go:~685`), so they never ask for `i < s`; if they ever do, the
snapshot is skipped, not written with a wrong `Conf`. `compact` and `maybeSnapshot` pass `ConfStateAt(applied)`. **The snapshot wire format and the stored
`Snapshot` shape do not change**: only the value placed in the existing `Conf` field does.
Related hypothesis (test 6): `baseConf` is set only at `NewNode` and `restore` (`node.go:199`, `snapshot.go:84`) and is not advanced when the node's own
`CreateSnapshot` compacts, so a later `rebuildConfig` (truncation or config append) replays the stale base over only the post-compaction suffix and may drop
compacted config entries. If red, the fix uses the same snapshot-based base; keep it in this card since it is the same "config as of an index" invariant. `CreateSnapshot` validation (reject a joint `Conf` with an empty `Incoming`) is out of scope.
