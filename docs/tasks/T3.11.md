## Goal
Show, with tests, what a node recovers after `ApplySnapshot` and a restart, decide whether that is a Log Matching or vote
problem, and decide the same for `roll()` segment naming after a suffix rewrite. Fix only what the evidence shows is wrong.

## Facts from the code
- `DiskStorage.ApplySnapshot` (`disk.go:303-331`) saves the snapshot, records `SnapshotMeta` in the WAL, then sets
  `s.entries = [{snap.Index, snap.Term}]` (`:325`), dropping **all** in-memory entries, then `TruncateBefore(snap.Index)` which deletes
  only whole segments below `index+1` (`wal.go:446-452`). Entries above `snap.Index` stay in the WAL; there is no "truncate suffix" record.
- On reopen, `OpenDiskStorage` keeps every replayed entry with `Index > snap.Meta.Index` (`disk.go:101-107`), so they come back.
- The core calls `ApplySnapshot` whenever the snapshot is newer than the commit index (`internal/raft/snapshot.go:50-59,76`), with no
  branch that keeps a matching suffix (paper §7: "if existing log has an entry with the same index and term as the snapshot's last
  included entry, retain the entries following it"). Pre-crash the node has only the snapshot; post-restart it has snapshot + stale tail.
- `CreateSnapshot` (`disk.go:238-276`) legitimately keeps the suffix and writes the same `SnapshotMeta` record; the WAL cannot tell
  "kept suffix" from "stale suffix" by itself.
- `roll()` names a new segment `lastIndex+1` (`wal.go:415`); after a suffix rewrite (`appendResolvingConflict`, `wal.go:259`)
  `lastIndex` can be lower than the previous segment's first index, so names are not monotonic. Order is by `seq` (`wal.go:154`).
  `TruncateBefore` stops at the first segment whose *next* `firstIndex` exceeds `index+1` (`wal.go:447-452`).
- A higher-term `RequestVote` makes `Step` call `becomeFollower` (`node.go:359-366`), which persists `(term, None)` (`:436`)
  **before** `handleVoteRequest` (`:381`, `election.go:42`): a rejection leaves `VotedFor == None` at the new term, not the old vote.
  PreVote (`election.go:121`) uses the same `isUpToDate`, so the pre-vote round regresses the same way.

## What is established and what is not
The snapshot (S,T) is committed. Any local entry at S with term t != T came from a leader of term < T, so the stale tail ends with a
term below T. **Established by inspection (reviewer, confirmed):** a restarted voter with snapshot (5,2) + stale tail 6..10 at term 1
compares candidates against `(10,1)` instead of `(5,2)` (`isUpToDate`, `log.go:58-64`). Candidate (12,1) is granted post-restart and
refused pre-restart; (7,1) and (4,1) are refused either way. This is a local vote regression.
**Not established: that it can elect a stale leader.** Counting argument to test, not assume, and it **holds only for fixed
membership**: with n = 2f+1 and an unchanging voter set, the quorum Q (f+1 nodes) that committed X=(S,T) holds X in its log. A node
regressed by this bug received X by InstallSnapshot after commit, so it is outside Q, as is the stale candidate E. Votes for E are
therefore at most 1 + (f-1) = f < f+1. It says nothing once membership differs: `rebuildConfig` re-reads ConfChange entries from the
log (`confchange.go:62-103`), so a stale tail can change the voter set and quorum after restart (test 3e, expected red). `ReadIndex`
or another path reusing the regressed `lastIndex()` is also open. Test 8 tries to break the fixed-membership argument; treat any
refuting test as a bug report. No Leader Completeness violation is claimed anywhere in this card.
- **Match index:** `maybeAppend` returns `lastNewIdx = prevIdx + len(entries)` (`log.go:87-88`), not the stored last index, so the
  success reply's `MatchIndex` (`replication.go:130-135`) is not inflated. A *rejection* hint uses the stored `lastIndex()+1` only
  when `prevIdx > lastIndex()` (`log.go:119-121`); otherwise it is the first index of the conflicting term (`log.go:123-137`). A hint
  can only lower the leader's `next` (`backoff`, `replication.go:193-195`).

## Approved fix (human approved a WAL format change, conditional on 3e being red)
**No backward compatibility is needed: there is no deployed data.** An older binary meeting the new record type may refuse it; that is accepted.
- **Record**: `recordDiscardSuffix recordType = 4` (`record.go:24-28`, plus the `String()` case "DiscardSuffix"). Framing is unchanged
  (`len u32 | crc32c u32 | type u8 | payload`, little-endian, `appendRecord`). Payload is exactly 8 bytes: `fromIndex u64` with the
  meaning "discard every entry with Index >= fromIndex". `decodeDiscardSuffix` uses `reader.uint64` then `atEnd`; `fromIndex == 0` and
  short or long payloads are `ErrCorruptRecord` (CRC-valid but undecodable = corruption, never a tear, as in T3.7).
- **Replay** (`replaySegment`, `wal.go:227-251`): new `case recordDiscardSuffix`: cut `rep.Entries` to those with `Index < fromIndex`,
  using the same `sort.Search` cut as `appendResolvingConflict` (`wal.go:259-265`). A `fromIndex` above the last entry is a no-op, not an
  error. Order in the log is the order of effect: entries appended after the discard re-extend the log. `rep.Snapshot` and `HardState` are
  untouched by it. `appendResolvingConflict` is unchanged.
- **Writer** (`ApplySnapshot`, `disk.go:303-331`), **mismatching path only**: the discard is written only when the local log holds an
  entry at `snap.Index` whose term differs from `snap.Term`, and there are entries above it to discard. A matching snapshot or one
  beyond the local log writes no discard record (decided, see "Matching snapshots"). Order: `Save` snapshot (`snapshot.go` already does
  temp, fsync, rename, directory fsync, so both the file and its directory entry are durable on return) -> **one WAL write holding
  `SnapshotMeta(S,T)` then `DiscardSuffix(S+1)`, fsynced before `ApplySnapshot` returns** (hence before the core acknowledges) -> memory
  update -> `TruncateBefore`. The discard is written **after** the snapshot is durable, never before: a crash between them would otherwise
  lose log entries without the snapshot that supersedes them. `CreateSnapshot` writes no discard (it keeps its suffix). Reject `S+1`
  overflow before saving. **There is no open-time reconciliation** (dropped: it could not tell a completed discard from a missing one, and
  could delete entries appended after the install).
- **Matching snapshots (decided): no discard record.** When the local log holds an entry at `snap.Index` with term equal to `snap.Term`,
  the Raft paper (§7) keeps the entries that follow, so `ApplySnapshot` writes no `DiscardSuffix`. Today's core nevertheless drops the
  suffix in memory (`disk.go:325`) while a reopen recovers it (`disk.go:101-107`). That memory/disk difference is **explicit and
  expected**, not a defect of this card. The executor confirms it is benign with `TestMatchingSnapshotMemoryDiskDifferenceIsBenign`:
  after a matching install and a restart the recovered tail entries are exactly the entries the cluster already agreed on (same index and
  term as the committed prefix; a leader append over them converges), votes use a `(lastIndex, lastTerm)` no more advanced than a node
  holding the matching entries legitimately has, and no `MatchIndex` or quorum claim exceeds what that node could legitimately have made.
  Any red result is reported first, not silently fixed.
- **Guarantee (narrow):** once `ApplySnapshot` has returned success for a mismatching snapshot, **no restart ever resurrects the discarded
  suffix**; entries appended after it are preserved across any number of restarts. Nothing is promised for a call that did not return.
- **Unacknowledged window (crash before `ApplySnapshot` returns):** the core has not acked, so the install never happened as far as the leader
  knows. Possible recovered states: (a) snapshot file absent: exactly the pre-install log; (b) snapshot file present, WAL meta and discard
  absent or torn: `OpenDiskStorage` loads the newer snapshot (`disk.go:85-91` allows it) and keeps replayed entries above it: boundary
  (S,T) plus the **pre-install tail**; (c) meta durable, discard torn or missing: same as (b); (d) both durable: snapshot plus empty tail.
  States (b) and (c) are safe because the node's claims equal the pre-install ones: `lastIndex` and the last term are those of the
  pre-install log, so `isUpToDate` votes are identical to pre-install votes; no `matchIndex`, vote or quorum claim exceeds what it could
  legitimately have made before the install (a durable snapshot is a committed (S,T), so claiming (S,T) at the boundary is true; the tail is
  replaced by any leader append through the normal conflict path); the recovered config is the pre-install config (joint A-E/A-F in the 3e
  fixture), which was already the in-effect config before the call. Test `TestUnacknowledgedInstallCrashWindowIsSafe` pins it (below).
- **Torn-tail repair interplay (T3.7):** `validRecordFollows` and the repair scan must know type 4 (extend its known-type table in the same
  commit as the record type). A torn `DiscardSuffix` at the tail is truncated like any torn record, which means "this install was never
  acknowledged" (state c). A CRC-bad discard with a valid record after it stays `ErrCorruptWAL`. A CRC-valid undecodable discard is
  `ErrCorruptWAL`.
- **Fuzz and property coverage:** `FuzzDecodeDiscardSuffix` (round-trip, like `FuzzDecodeEntry`, `fuzz_test.go:35`); `FuzzReadRecord` seeds gain
  a type-4 record; the T3.7 replay-tail fuzz generator and its independent frame walker learn type 4; a replay model test applies random
  sequences of Entry / HardState / SnapshotMeta / DiscardSuffix records and compares `Open`'s result with a simple in-memory model (500 seeds).
- **Crash points** (faultfs, every op in `ApplySnapshot` of a mismatching snapshot, modes drop and torn x seeds 1-5), **run under
  `SyncAlways` only** for "Open succeeds" and the assertions below. Crashes classified by whether `ApplySnapshot` returned:
  - **Returned success** then `Crash`, then reopen, then **restart twice** (a second reopen with no new writes, then a reopen after new
    appends 6.. at term 2 that are made **durable** first: `SyncAlways`, or an explicit `WAL.Sync()` / `SyncAll()` before the crash, so
    the assertion never depends on unsynced bytes): snapshot + empty tail; entries appended after the install survive every restart; the replayed discard is
    idempotent and a surviving old boundary entry (5,1) in the WAL re-triggers nothing (no second discard, no deleted later entry).
  - **Did not return** (every earlier crash point): `TestUnacknowledgedInstallCrashWindowIsSafe`: the recovered store is state (a), (b),
    (c) or (d) above and `validateContiguous` passes. For (b) and (c), raft-level assertions on a node built from it use the **weaker
    oracle** (claims are *not* identical to pre-install: the recovered boundary is (5,2) where the pre-install log held (5,1)):
    1. **Votes are identical** to the pre-install node's for candidates (12,1), (7,1), (4,1), (5,2), (6,2) at term 3 (`isUpToDate` compares
       the same last index and term, `log.go:58-64`).
    2. **The snapshot boundary may be acknowledged.** An empty AppendEntries with `prev=(5,2)` succeeds with `MatchIndex == 5` (the
       recovered `Term(5)` is the snapshot's term, so `matches` holds, `log.go:50-56`); the pre-install node would have rejected it
       because its entry 5 had term 1. This is accepted: (5,2) is a committed boundary, so the claim is true.
    3. **Nothing beyond the boundary is acknowledged before conflicting entries are replaced.** For an AppendEntries `prev=(5,2)` carrying
       entries 6.. at term 2, the success reply's `MatchIndex` equals `prev + len(entries)` and storage has already replaced the
       conflicting term-1 entries at those indexes (`maybeAppend`, `log.go:82-105`); a heartbeat advertising `prev=(8,2)` or
       `(10,1)` is rejected; no `MatchIndex` exceeds 5 without such a replacing append.
    4. Config and quorum equal the pre-install ones (joint A-E/A-F in the 3e fixture); commit index never exceeds the snapshot index.
  - **`SyncNever` variant** (power loss can tear a sealed segment when the combined write triggers a roll, `wal.go:388-392,410-415`;
    replay refuses a torn non-last segment, `wal.go:196-199`): depends on **T3.12** (sync the old segment in `roll`). Until T3.12 lands
    the variant asserts only the contract (no hole, no reorder, success when no roll occurred) and expected `ErrCorruptWAL` for rolls is
    listed as a known failure, not asserted green. After T3.12 it asserts "Open succeeds" too.
