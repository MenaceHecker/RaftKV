# T3.11: ApplySnapshot and stale on-disk entries; roll() naming after a suffix rewrite

Planner: Claude, read-only. Based on `internal/storage` and `internal/raft` at 6018e7b. Branch: `test/t3-11-snapshot-recovery`
(becomes `fix/...` if evidence demands a fix). **Depends on T3.8 (faultfs)**, hence T3.6 and T3.7.
This card is investigation first: characterisation tests, a written decision, then a fix only if the evidence says so.

## Goal
Show, with tests, what a node recovers after `ApplySnapshot` and a restart, decide whether that is a Log Matching or vote
problem, and decide the same for `roll()` segment naming after a suffix rewrite. Fix only what the evidence shows is wrong.

## Facts from the code
- `DiskStorage.ApplySnapshot` (`disk.go:303-331`) saves the snapshot, records `SnapshotMeta` in the WAL, then sets
  `s.entries = [{snap.Index, snap.Term}]` (`:325`), dropping **all** in-memory entries, then `TruncateBefore(snap.Index)` which deletes
  only whole segments below `index+1` (`wal.go:446-452`). Entries above `snap.Index` stay in the WAL; there is no "truncate suffix" record.
- On reopen, `OpenDiskStorage` keeps every replayed entry with `Index > snap.Meta.Index` (`disk.go:101-107`), so they come back.
- The core calls `ApplySnapshot` whenever the snapshot is newer than the commit index (`internal/raft/snapshot.go:46-58,76`), with no
  branch that keeps a matching suffix (paper §7: "if existing log has an entry with the same index and term as the snapshot's last
  included entry, retain the entries following it"). Pre-crash the node has only the snapshot; post-restart it has snapshot + stale tail.
- `CreateSnapshot` (`disk.go:238-276`) legitimately keeps the suffix and writes the same `SnapshotMeta` record; so the WAL cannot tell
  "kept suffix" from "stale suffix" by itself.
- `roll()` names a new segment `lastIndex+1` (`wal.go:415`); after a suffix rewrite (`appendResolvingConflict`, `wal.go:259`)
  `lastIndex` can be lower than the previous segment's first index, so names are not monotonic. Order is by `seq` (`wal.go:154`).
  `TruncateBefore` stops at the first segment whose *next* `firstIndex` exceeds `index+1` (`wal.go:447-452`).

## Hypothesis to test (not established; two directions, one of them worrying)
The snapshot (S,T) is committed. Any local entry at S with term t != T came from a leader of term < T (a leader of term > T must
contain (S,T), Leader Completeness), so the stale tail ends with a term below T.
- **Restarted node as candidate or leader:** its last term is below every voter's (>= T), so it loses elections. Likely safe.
- **Restarted node as voter: the dangerous direction.** `isUpToDate` (`log.go:58-64`) compares the candidate to our `lastTerm()`.
  Pre-crash that was T (snapshot boundary); post-restart it is the stale tail's term t < T. A candidate whose log is *behind the
  snapshot* (last term t, or even lacking committed entry (S,T)) can then look "up to date" against the regressed log and **win this
  node's vote**. One regressed voter is not a majority, but it is a Leader Completeness / vote-safety hole whose size depends on how
  many nodes can be in this state at once. The question for the tests is exactly this: does the node grant votes, or inflate its
  match index, using the regressed log?
- **Match index:** `maybeAppend` returns `lastIndex = prevIdx + len(entries)` (`log.go:82-84`), not the stored last index, so
  `MatchIndex` in a success reply (`replication.go:127-133`) should not be inflated. A *rejection* hint uses the stored
  `lastIndex()+1` (`log.go:119-121`), which is inflated (stale M+1) but only lowers the leader's `next` (`backoff`, `replication.go:178-181`).
  A conflicting match at (S+k, same term) is argued impossible by Log Matching of the original logs. Tests, not argument, decide.
Treat any refuting test as a bug report.

## Decision rule (executor records it under "Findings" before any fix)
- Test 3a decides. If every behind-the-snapshot candidate is refused, 3b/3c hold and 4-6 pass: classify as "recovered log differs from
  the pre-crash log; Log Matching, vote and match index are safe". No fix here (OPEN QUESTIONS 1).
- If 3a grants any vote that the pre-crash node would have refused, or 3b/3c show an inflated match or commit: it is a safety bug
  (vote regression after InstallSnapshot). Stop, put the failing sequence first in the report, and propose the red-first fix card only
  after the human agrees. Candidate fixes for the human (not chosen here): (a) a durable "discard entries above S" WAL record written
  by `ApplySnapshot` (format change, needs a compat note); (b) implement §7 properly: keep the suffix if (S,T) matches, otherwise discard
  with the discard made durable; (c) on open, drop entries above the snapshot unless the log's term at S equals the snapshot's
  (`CreateSnapshot` and `ApplySnapshot` write identical `SnapshotMeta` records today, so the WAL cannot tell them apart without a new field).
- Part B: if tests 7-9 pass, record "benign: names are non-monotonic but `TruncateBefore` only retains extra segments". If they fail, the
  fix is in `roll`/`TruncateBefore` with the failing sequence as the red test.
