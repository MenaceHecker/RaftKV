## Goal
`TestFollowerCatchesUpFromALargeBacklog` (`internal/transport/replicationsize_test.go:19`) failed once in CI after `grpcSettleTimeout` (20s,
`peer_test.go:25`) on a 2-core runner under `go test -race ./...` next to a 250s package. Decide, with evidence, between (A) CPU starvation
only and (B) a real replication-recovery weakness after outbound queue overflow, then fix B if it is real. §6.4: one failure is a P0.

## The failing run (raw, from the CI log)
Node 1 leader commit=65 applied=65; node 2 (restarted follower) commit=57 applied=57; node 3 caught up. Links: 1->2 sent=1193 dropped=1717
failed=230; 2->1 sent=1190 dropped=0 failed=0; 3->2 sent=1. Prior: 30 CI runs green on main; local 15/15 alone, 15/15 at GOMAXPROCS=2 under
load, 40/40 at GOMAXPROCS=1 under 8 CPU-heavy processes (all `-race`). Not reproduced.

## Facts from the code (read at 8e00a77)
1. **No state exists that only a response can unblock the leader.** `progress` has `next, match, heldBack, active` only (`raft/node.go:111`);
   no probe/replicate mode, no inflight window, no paused flag. `sendAppend` (`raft/replication.go:58`) is stateless: it builds
   `entriesFrom(pr.next)`, cut by `limitEntries` at `MaxAppendBytes` = 1 MiB (`raft/node.go:11,17`, `replication.go:77`). Every heartbeat tick
   calls `broadcastHeartbeat` -> `broadcastAppend` -> `sendAppend` for each peer (`replication.go:48-56`), driven from `Tick` (`raft/node.go:333-336`).
   `pr.next` moves only on a success response (`:157-162`) or down on a rejection (`backoff`, `:152,194`); it is never advanced optimistically.
   So a dropped request or dropped response is retried by the next heartbeat tick (10 ms here, `HeartbeatTick: 1`, `TickInterval: 10ms`).
   By reading, a permanent stall after queue drops is **not possible in the leader's raft state**. Confidence: high for the raft core; the one
   thing not read is every `Tick` caller path under a paused/slow node loop (see fact 6).
2. **Every tick re-sends the same <=1 MiB batch** while the follower has not answered, so one slow follower makes the leader enqueue ~100
   near-identical 1 MiB messages per second (`valueSize` = 128 KiB, so one append carries about 7-8 entries: the "8 entries behind" is about
   one `MaxAppendBytes` slice; may be coincidence, unverified). A success response with `heldBack` (`:170`) also enqueues a further append.
3. **Outbound path** (`transport/peer.go`): `Send` (`:196`) does a non-blocking enqueue into a 256-slot channel (`DefaultQueueSize`, `:21`)
   and **drops the newest** message when full (`:219-222`, counted in `dropped`). One goroutine per peer (`run`, `:226`) delivers **serially**,
   one blocking unary RPC at a time with a 5s timeout (`:239-254`, `DefaultSendTimeout` `:23`). Queued messages are never superseded or
   coalesced, so a full queue holds up to 256 stale appends (up to ~256 MiB) ahead of any fresh message. Draining takes 256 x per-RPC latency;
   at ~80 ms per 1 MiB RPC under `-race` on starved cores that is ~20 s (**the 80 ms is an assumption, not measured**).
4. **Inbound drop is silent and uncounted**: `node.Step` is non-blocking with a 256-slot `recvc` and a `default:` that discards (`node/node.go:287-293`,
   `:263`); `RaftServer.Deliver` still answers OK (`peer.go:352-361`), so the sender counts it as `sent`. A starved follower loop can discard
   appends with no counter anywhere.
5. **What the counters imply (inference, not proof).** `failed=230` cannot be 5s timeouts (230 x 5s >> the test's duration, deliveries are
   serial), so these were fast failures, most likely connection-refused while node 2 was down (unverified: counters carry no timestamps).
   `dropped=1717` is about 17 s of one enqueue per 10 ms tick: consistent with the 1->2 queue being **full for nearly the whole 20 s wait**, i.e.
   the link delivered far slower than the leader enqueued. `dropped=0` on 2->1 means responses (small) were never the bottleneck. `sent` on
   1->2 and 2->1 are equal to within 3 and cover the whole test life, so they say nothing about the catch-up phase. Node 2 stuck at 57 with the
   queue full fits "slow drain of stale appends" (hypothesis H2); it also fits "follower loop starved or discarding at `recvc`" (H3).
6. A **node-level** stall is not excluded: if node 2's `Tick`/`Step` loop (`node/node.go:385-444`) is slow, its inbound `recvc` fills (fact 4)
   and appends vanish; the leader keeps resending (fact 1) so it still converges once the node is scheduled. Not a deadlock by reading.

## Hypotheses (ranked by the planner; all unverified)
- **H1 CPU starvation only** (the main session's view): ~45% . Test run slow because the host is saturated; the 1 MiB batches amplify it.
- **H2 head-of-line staleness / no flow control** (duplicate 1 MiB appends fill the queue and delay the fresh one): ~40%. A real design
  weakness that turns starvation into a >20 s stall; not a safety bug, a liveness-latency bug. Fix is cheap.
- **H3 silent inbound drops at `recvc`**: ~10%, overlaps H1/H2.
- **H4 a true raft liveness bug (leader stuck, follower rejecting forever)**: <5% by reading. No code path found; stays open until test R1/R2 are green.

## Fix options (apply only the one the evidence supports; human review of each)
- **If H4**: fix in `internal/raft` (replication/progress) with R1 as the regression test; cite paper §5.3 (log replication, retry), §5.2 heartbeats.
- **If H2** (preferred when queue staleness is shown): (a) in `peer.go`, coalesce per peer: a newer `MsgAppendRequest` replaces a queued older one to
  the same peer (keep heartbeats, votes, responses ordered; never merge across terms); or (b) bound the leader's in-flight appends per follower
  (raft-level probe/replicate window; larger change, raft review); or (c) enqueue-time drop of the **oldest** append instead of the newest. Start with (a)
  or (c): transport-only, no raft change. Snapshots (`deliverSnapshot`, `:256`) are never coalesced away.
- **If H3**: make inbound loss observable (counter in `node.Step`, surfaced in `dump()` and metrics) and reconsider the 256-slot `recvc` vs the
  1 MiB messages; raft semantics unchanged.
- **If H1 only**: no production change. Keep the test as is, document the CI environment finding in the PR, leave T1/T2 as a recorded decision;
  still file the 1 MiB x 100/s amplification as a backlog item.
- **In every case**: the PR logs the root cause (§6.4) and the evidence from the table above.
