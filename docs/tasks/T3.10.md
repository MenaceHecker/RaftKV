# T3.10: TruncateBefore must sync the replacement HardState before deleting old segments

Planner: claude, read-only. Based on `internal/storage/wal.go` at 6018e7b. Branch: `fix/t3-10-compaction-hardstate`.

**Depends on T3.8 (faultfs)**, hence T3.6 and T3.7. Does not need T3.9. Red commit, then fix commit, separate.

## Goal
`TruncateBefore` (`wal.go:431-469`) re-records HardState into the active segment and then deletes older segments, which may hold
the only durable copy of the term and vote. Under `SyncNever` the new record is not fsynced (`write` syncs only for `SyncAlways`,
`wal.go:402`), so power loss after the deletes can roll `currentTerm`/`votedFor` back. Sync it first, in every fsync mode.

## Why this is a safety problem
A node that forgets `votedFor` or a higher `currentTerm` can vote twice in a term or accept a stale leader (Raft paper Figure 2,
persistent state; §5.2, §5.4). RUNBOOK §7.2 item 1 requires HardState to be durable before it is relied on. `--fsync=false`
(`cmd/raftkv-server/main.go:67`) documents "survives a process crash but not power loss", but losing the *old* record because of our
own delete is a self-inflicted rollback beyond what the flag promises, and it affects any crash that follows the delete.

## Invariants touched (RUNBOOK §7 refs)
§7.2 item 1 (term and vote durable); §7.3 #3 (prefix compaction crash-safe: "persist the intent before deleting data"); §7.5.

## Behavior specification
- In `TruncateBefore`, after writing the HardState record (when `!w.hardState.IsEmpty()`), call `w.active.Sync()` unconditionally,
  before the first `Remove`. If the sync fails: poison the WAL (T3.9 if merged, else return the error) and delete nothing.
- If nothing is going to be deleted (`keepFrom == 0`, `wal.go:454`), no extra sync is needed; keep the early-return before the sync
  or sync once only when a delete will follow. The tests cover both.
- Order inside the delete loop (oldest first, then one `SyncDir`) is unchanged.
- `SyncAlways` behavior is unchanged: the record is already synced by `write`; the explicit sync is then a second, cheap fsync.
  Executor may skip the extra call when `policy == SyncAlways`; either way the tests below hold.

The `roll()` fsync is a separate card: T3.12.
