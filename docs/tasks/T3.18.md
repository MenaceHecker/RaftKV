# T3.18: protect membership changes and bound snapshot streams on the shared listener

Planner: Claude, read-only. Based on `origin/main` ea0dd7a (T4.7 merged). Claims come from reading; **no test was run**.
Branches: `test/t3-18-shared-listener-red`, then `fix/t3-18-shared-listener`. Origin: T4.7 decision 6 and Codex's review of that card.
Not on the demo critical path unless the demo exposes the shared port beyond a trusted network (see OPEN QUESTIONS 1).

## Goal
Two pre-existing exposures on the shared listener (client plus peer port) let an unauthenticated caller who can reach it damage a cluster,
independent of the admin controls from T4.7: (a) `ClusterService.AddNode`/`RemoveNode` change membership with no authorization;
(b) `RaftService.DeliverSnapshot` buffers up to 1 GiB per stream with no aggregate or concurrency bound. Fix (a) with a token on the two
mutating methods and (b) with byte and stream budgets. Raft behaviour and the wire format do not change.

## Invariants touched
RUNBOOK §7.1 not affected (the Raft core is untouched). Availability and safety of membership: an unauthorised `RemoveNode` of reachable voters
or `AddNode` of unreachable ones can cost quorum. Process survival under memory pressure. `internal/raft` is not edited.

## Facts from the code (ea0dd7a)
- `KVServer.Register` puts `KVService` and `ClusterService` on the shared server (`kvserver.go:47-49`); `AddNode` (`:180`) and `RemoveNode`
  (`:194`) call the store with no credential check. `ListMembers` is read-only and stays open.
- The shared server is `grpc.NewServer()` with no options (`cmd/raftkv-server/main.go:340`) unless pause is on, when only the pause interceptors
  are installed (`:337`). There are no size, stream-count or keepalive limits.
- `DeliverSnapshot` (`peer.go:364`) appends every data frame into one slice until `MaxSnapshotBytes` = 1 GiB (`:362,390-393`); N concurrent
  streams hold N GiB. The header frame arrives first (`:408` decodes it after the loop), but the sender is not checked before data is buffered.
- `Deliver` is unary and bound by gRPC's 4 MiB default receive limit. Raft peers authenticate nothing today (no TLS, no token).
- The T4.7 admin interceptors (`admin.go:340`, `NewAdminInterceptors`) and `LoadAdminToken` already implement bearer-token checking with a
  constant-time compare; reuse them rather than writing a second implementation.
- `docs/deployment.md:218` tells operators to call `AddNode` through `ClusterService` after scaling a StatefulSet, so any protection must keep
  that path usable (with a credential).

## Files to create or change
- `cmd/raftkv-server/main.go`: new `--cluster-token-file` (off by default = today's behaviour) installing an interceptor on the shared
  server for exactly `/raftkv.v1.ClusterService/AddNode` and `/RemoveNode`; fail closed if the flag is set with an unusable file.
- `internal/transport/admin.go` (or a new `internal/transport/guard.go`): a method-scoped token interceptor reusing the existing checker.
- `internal/transport/peer.go`: `snapshotBudget` (total in-flight bytes and concurrent streams, with defaults) consulted in
  `DeliverSnapshot`: reserve before buffering each chunk, release on return (all paths, including errors and cancellation); over budget
  returns `ResourceExhausted` and discards the stream.
- `internal/transport/kvserver.go`: no behaviour change besides the interceptor wiring.
- `docs/deployment.md`, `docs/observability.md`: the credential for `AddNode`, the new budgets, and what remains unprotected.

## Implementation notes
- Reserve per chunk, not once for the declared maximum, so a small snapshot does not hold a large reservation; release in a `defer`.
- Do not log the token or request payloads. Same constant-time compare as T4.7.
- The budget is a safety net against exhaustion, not a rate limiter; it does not authenticate peers.

## Acceptance criteria
Unauthenticated `AddNode`/`RemoveNode` refused when the flag is set, unchanged when off (tests 1-4); aggregate snapshot memory and stream count
bounded with all paths releasing (5-9); the existing InstallSnapshot tests pass unchanged (10); `make fmt vet lint test`;
`go test -race -count=20` on `internal/transport`.

## Out of scope
mTLS or any authentication of Raft peer traffic and of `Deliver`; authentication of `KVService` clients; rate limiting; rejecting snapshot
senders that are not cluster members (needs a membership query on `Stepper`, see OPEN QUESTIONS); changing `MaxSnapshotBytes`; `internal/raft`.

## OPEN QUESTIONS for the human
1. **Is this needed before the demo?** If the shared port is reachable only inside a private subnet (RUNBOOK §10.4), T3.18 can wait; if the
   gateway or the public internet can reach it, it should land first.
2. **Token flag vs moving membership to the admin listener.** The card assumes a separate `--cluster-token-file` on the shared port (keeps the
   deployment guide's flow). Alternative: serve `AddNode`/`RemoveNode` only on the admin listener, which breaks that flow.
3. **Defaults.** Proposed: 256 MiB aggregate, 4 concurrent snapshot streams. Confirm or give numbers based on the largest expected snapshot
   (RUNBOOK sizes are not stated; `docs/benchmarks.md` has none for snapshots).
4. **Reject non-member senders?** Cheaper and stronger than a budget alone, but `Stepper` has no membership query and peers carry no
   credentials, so a forged sender id defeats it. The card leaves it out; say if you want it as a follow-up.
