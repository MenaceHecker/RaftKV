## Goal
`AppendEntries` encodes every entry as one record with no size check (`wal.go:350-353`), but `readRecord` rejects any record whose
body exceeds `maxRecordSize` = 64 MiB (`record.go:19`, `:77-79`). An entry with a body over the limit is written, fsynced and
acked, and the next open fails with `ErrRecordTooLarge` (the tail repair of T3.7 may even drop it as a torn record, losing an acked
write). Snapshots already check their size (`snapshot.go:97-100`, `ErrSnapshotTooLarge`). Reject such entries **before writing a
byte**, and cap proposal size at the node API so a client request cannot reach the limit.

## Severity and reachability (be honest in the PR)
Not reachable through the default network API: `grpc.NewServer()` (`cmd/raftkv-server/main.go:171`) has no size options, so gRPC's 4 MiB
receive limit applies, far below 64 MiB. It is reachable in-process (`node.Propose`, `raft.Node.Propose`), if limits are raised, or by
future code paths. A latent hardening bug, not a remotely triggerable one today. One more reason for the node-level cap: a rejected
`Append` surfaces as `ErrStorage`, which `fatal()` treats as fatal (`internal/node/node.go:554`), so without a cap one oversized
proposal would stop the leader instead of failing one request.

## Invariants touched (RUNBOOK §7 refs)
§7.2 item 1 (an acked record must be replayable; do not ack what recovery will reject); §7.3 #1 (record framing); §7.3 #4.

## Behavior specification (decided)
- Encoded size of an entry record body is `typeSize + len(encodeEntry(e))` = `1 + 32 + len(e.Data)` (term, index, type, length prefix,
  data; `record.go:146-151`). Reject when it exceeds `maxRecordSize`. Largest accepted `Data` is `maxRecordSize - 33`; export it as
  `storage.MaxEntryData`. Boundary: exactly at the limit is accepted (matches `readRecord`: `bodyLen > maxRecordSize` is the failure).
- `WAL.AppendEntries` validates **every** entry in the batch (after the contiguity check, `wal.go:343-348`) before encoding or writing
  any of them. On failure it returns a new `ErrEntryTooLarge` (wrapped with index and size, `errors.Is` works) and changes nothing:
  segment bytes, `activeSize`, `lastIndex`, `hardState`. It does **not** poison the WAL (T3.9): nothing was written.
- `DiskStorage.Append` returns the error unchanged and leaves memory untouched (already true at `disk.go:229-235`).
- `internal/node`: `Config.MaxProposalBytes` (default 1 MiB, OPEN QUESTIONS 1), validated `<= storage.MaxEntryData` in
  `validate()` (`node.go:93`). `Node.Propose` (`node.go:287`) checks `len(cmd.Encode())` before enqueueing and returns
  `ErrProposalTooLarge` without touching raft. No change in `internal/raft`.
